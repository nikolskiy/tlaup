# TLA+ specs of the design

Three small TLA+ specs of the parts of the tlaup design where several processes change shared state in steps that can interleave, checked with TLC before any of it is built (roadmap decision D46; the plan is [design 03, part 2](../docs/design/03-run-stages-and-specs.md#part-2-tla-specs-of-the-design)). They are not part of the product and nothing imports them.

Written and checked on 2026-11-18 by one agent; reviewed and signed off later (next paragraph). Each spec models a design section as it was written on that day, not as it could be designed; where a spec found the section wrong or silent, the fix is in the section, marked "formal check". The maintainer walked through the results the same day and settled two of the three points left open (decisions D49 and D50); the run-folder configs were switched to D49 and checked again (below).

**Revised 2026-11-20** by the stage 3 design agent, for decisions D51 to D53 (the answers to investigation questions 25, 30, 33, 34 and 35; [summary](../docs/design/top-up-incorporation-2026-11-20.md)). `RunFolders` now hands a killed tlaup's locks to its TLC where the system allows it and lets that TLC end in the end, asks per run whether to keep, writes checkpoints in two steps, and has variants for Windows and for a lock library that unlinks on release. `Signals` now has a tlaup that dies at any moment and a first signal that waits for a checkpoint. `ToolStore` is unchanged. Every config was checked again. The stateful tests were brought up to the revision the same day ([design 03](../docs/design/03-run-stages-and-specs.md#specs-and-their-tests), "What the stateful tests gained").

**Reviewed 2026-11-20** by a fresh agent ([review](../docs/design/review-2026-11-20-formal-check.md)), and its findings worked in the same day: a kept folder could be deleted by a second resume (FC1, now K1-9), the configs never had more than two runs (FC2), `NoDuplicate` was vacuous (FC3), `PinConsistent`'s exception was too wide (FC4), an install did not repair the pin a killed uninstall left (FC5), and smaller points; decision D60 (the JVM of a parsed run in a process group of its own) came from finding TU1. `RunFolders` gained `KeptMeansKeep`, `ToolStore` `CheckInstalled` and a narrower ghost, and both were checked again with `Signals`; the tables below are from that run. Signed off by the maintainer on 2026-11-21, with no second review of the fixes; stage 4 may start.

## Checking them

```bash
TLA2TOOLS=<path to tla2tools.jar> ./check.sh
```

`check.sh` runs TLC on every `.cfg` here and under `variants/`, and compares the result with the first line of the `.cfg`, which says what TLC should report: `ok`, or the property that is violated. A pattern runs a part: `./check.sh Signals`. One config by hand:

```bash
java -cp <path to tla2tools.jar> tlc2.TLC -workers auto -config variants/RunFolders-no-recheck.cfg RunFolders.tla
```

It needs Java 11 or newer and a released `tla2tools.jar`; the tlaup these specs describe does not exist yet. TLC's state files go to `states*/` beside the specs, which `.gitignore` covers.

The results below are from one run of `check.sh` on 2026-11-20 and 2026-11-21, after the findings of the review were worked in: TLC 2026.05.26.235334 (rev 4ba7d88; the jar published under the tag `v1.8.0` on 2026-05-26, SHA-256 `237332bd…2a4fb`), OpenJDK 25.0.5, Linux, 12 cores, `-workers auto`, breadth-first. All 34 configs came out as their first line expects, in 3 h 41 min for the whole set; four configs take most of it (`RunFolders`, `one-process-three-ids`, `windows` and `no-hour-rule`, 41 to 65 minutes each). Every config was run, not only those whose rules changed: the fix of FC1 (`KeptMeansKeep`) changes what settle and a resume do in every RunFolders config with `-recover`, and FC4 and FC5 change `PinConsistent` and `PinStep` for every ToolStore config, so no config could be shown unaffected by reading alone; Signals changed only in a comment and was run with the rest. The run before, of 2026-11-20 after the revision for D51 to D53 (31 configs, 1 h 44 min, plus 55 min for `windows` once `windows-checkpoint` was split from it, finding K1-8), and the runs of 2026-11-18 used the same TLC, Java and machine; their numbers are in this file's history.

A spec has three kinds of config. The one named after it is the design as written, with every property that should hold. A variant with `expect: ok` is the design under another answer to an open question, or with an option the maintainer did not take. A variant with `expect: violated` shows that a property does not hold, on purpose: a finding, the reach of a risk the design accepts, or a first wording of a property that said too much. TLC stops at the first violation, so those state counts are not sizes and change a little from run to run.

### What the maintainer chose

Each was written into its design section with the options and their costs, and the maintainer chose on 2026-11-18, walking through these results.

1. **`cache clean` and the checkpoint of a killed run** (K1-4, [R6](../docs/design/11-runner.md#r6-run-folders), constant `CleanSparesCheckpoint`): spared unless `--all` is given (decision D49). The configs now have the constant on, except `checkpoint-clean`, which shows the option not taken.
2. **What a SIGKILL of tlaup reaches** (K1-3 and K1-5, [R6, Risks](../docs/design/11-runner.md#r6-run-folders)): not chosen on 2026-11-18. The maintainer added a fourth option, making TLC end with tlaup, and prefers it; question 35 asks whether it can be done. Chosen on 2026-11-20, after questions 33 to 35 (decision D51): the fourth option on every system, the lifeline agent, together with the third on Linux and macOS, the JVM inheriting the run's locks. The spec models both: `Kill` hands the locks to the orphan TLC with `LockFollowsTLC`, and `OrphanExit` is fair. The same day the maintainer settled how checkpoints are trusted and when a folder is kept (D52, D53), which the spec models too.
3. **The order of the two steps of uninstall** (K2-2, [V3](../docs/design/12-tools-and-downloads.md#v3-uninstall), constant `UnpinFirst`): the order stays, and the dangling pin after a kill is accepted (decision D50). `unpin-first` shows the option not taken.

Settled at the same time, from the agent's report on this work ([feedback](../docs/feedback/2026-11-18-tla-tools-as-an-agent.md), point 5): `tlaup tlc --no-keep`, and no kept folder for a run stopped with no intent to resume (decision D48). Neither the spec nor the stateful test modelled it then. D53 (2026-11-20) made not keeping the default and replaced `--no-keep` with `--keep`; the spec models it as `keep` per run.

## RunFolders

**Models.** Two or three tlaup processes. A run is the steps of R6 "Start" one at a time: create the lock file; take its lock (an open and a flock, apart); for `-recover`, take the recovered folder's lock; make the folder; write `run.json`; sweep. Then TLC, which may write a checkpoint at any moment or never; settle; and the end, where the folder is kept and released, or deleted with its lock file and released, first the run's own and then the recovered one. A sweep and `cache clean`, with and without `--all`, list the entries and visit each: open its lock file, try the lock once, look and act, release. Any step of a start can fail, a lock wait can time out, and a tlaup can be killed anywhere: its locks are released and its TLC runs on. A lock file ages past one hour at any moment.

Since 2026-11-20: each run is started with or without `--keep` (`keep`), and a run that resumes from a folder whose run asked is a kept run too. TLC writes a checkpoint in two steps, the `.tmp` files and then the commit, and a TLC that stops between them leaves a checkpoint that is not complete; it may write again over a complete one. Settle keeps a folder only when the run did not finish, asked to be kept and holds a complete checkpoint; the sweep never removes a kept folder, removes an unsettled one at once unless it asked and is complete, and removes one with no `run.json` only when it finds it over 30 days old; `cache clean` spares an unsettled resumable folder. With `LockFollowsTLC` a kill hands the run's own lock and the recovered folder's lock to the TLC instead of releasing them (two more lock objects per run, `TLCOwn` and `TLCRec`), and the TLC's end, `OrphanExit`, releases them, as the operating system does when the JVM's last descriptor closes; nothing is unlinked then. Under `FairSpec` the orphan's end is fair: the lifeline. With `UnlinkOnRelease` a visit's `FileLock` also unlinks the name when it releases; a run's own and recovered locks are tlaup's `RunLock`, which never does.

Names and files are apart, as the plan asked: a lock is on a file, a lock file is opened by name and created when it is not there, and an unlink removes whatever file is at the name. That is the behaviour of `open`, `flock` and `unlink`, and of the lock library as read from the source of `filelock` 4.2.10.

**Leaves out.**

- Ages of folders are not state. Each visit of a sweep chooses what it finds: young, over a day, over 30 days. That lets every order of ageing happen, and more (a folder can look old and then young); it hides K1-5.
- "Delete the folder, remove the lock file" is one step. A deletion can fail and leave the folder; it cannot remove half of it.
- A run with the user's own `-metadir`; a folder made by a command pasted from `--show-command` (a folder with no `run.json` exists in the model only between two steps of a start, or after a kill there).
- What is inside a folder beyond "has `run.json`", "is kept", "has a checkpoint". The note and the resume command.
- Windows' file semantics, where an open file cannot be deleted and the lock is not `flock`. The Windows variants keep POSIX files and only switch the inherited lock off, which is what they are for: the window the lifeline alone leaves. The release-time unlink is left out for Windows on purpose, with this argument (question 30, [research 30](../docs/research/30-library-behaviours.md)): on Windows every `filelock` version deletes the lock file on release, but Windows refuses to delete a file that any process has open, and every holder and every waiter keeps the lock file open without delete sharing; so the delete at release removes the file only when nobody holds or waits on it, and cannot remove another holder's file. The research's probe found exclusion intact on Windows in every version, 3.20.3 included. D15 asks no more.
- More than one SIGKILL in a behaviour.
- The time the lifeline takes (about two seconds): the orphan's end is some later step, which lets every interleaving happen in between.
- `cache clean <run-id>` (D53) as an action of its own: it is `cache clean --all` for one entry, and the model's `--all` visits each entry by the same step, so `KeptSurvives` allows it through `CleanAllStep`.

**Properties.** `NoDeleteUnderTLC`, `OneTLCPerFolder`, `KeptSurvives`, `LockExclusive` and `NothingLeft`, as [03 lists them](../docs/design/03-run-stages-and-specs.md#k1-run-folders). Added: `HeldIsCurrent` (a held lock is on the file at the name), `LiveRunLocked` (a live run that has made its folder holds a current lock on it, and with `LockFollowsTLC` so does the TLC of a killed one), `CheckpointSurvives` (K1-4), `KeptIsComplete` (settle keeps only a complete checkpoint, D52) and `LockExclusiveUntilRelease`, which is expected to fail (K1-1). Revised 2026-11-20: `NoDeleteUnderTLC` and `OneTLCPerFolder` no longer have an exception for a killed tlaup (they were weaker until D51, and their exception-free forms, `NoDeleteUnderOrphanTLC` and `OneTLCPerFolderAfterKill`, failed); the weaker forms are kept as `NoDeleteUnderLiveTLC` and `OneTLCPerFolderUnlessKilled` for the Windows variant. `KeptSurvives` says that only `cache clean --all` and the end of a run that resumed from a kept folder and finished remove it; no sweep does (D53). `CheckpointSurvives` says the same for every folder of a run that asked to be kept and holds a complete checkpoint, unless its own run finished. `NothingLeft` excludes the folders that stay on purpose: kept, or unsettled and resumable.

**The two questions.**

1. *Can a process that opened the old file and one that creates the new one both believe they hold the lock?* With `Recheck` (the lock library looks at the link count of the file it locked, and tries again if it is zero): no, in every config checked. Without it: yes (`three-no-recheck`), and with two processes one of them holds a lock on a file that is no longer at the name (`no-recheck-stale`).
2. *Does the one-hour rule close the gap between creating a lock file and locking it?* With `Recheck` the gap is closed without the rule: `no-hour-rule` passes with the rule switched off, because a start whose lock file is removed under it creates a new one and locks that. Without `Recheck` the rule is what closes it: `no-recheck` passes, `no-recheck-no-hour-rule` fails, and so does `no-recheck-stall`, where the rule is on and an hour passes while a run is between its steps.

**Results.** Constants not named are those of `RunFolders.cfg`: two processes that may each do everything, two run ids, six lock files at once, one SIGKILL, `Recheck`, `HourRule`, `Stall` (an hour can pass during a start or a visit), `DeleteMayFail`, `CleanSparesCheckpoint` (since decision D49), `LockFollowsTLC` (since D51) and `KeptMeansKeep` (since the review, FC1) on, `UnlinkOnRelease` off. The revision for D51 to D53 made the main model about six times larger (16.6 million distinct states before, 97.4 million after), mostly from `keep`, the two-step checkpoint and the orphan's locks; with `KeptMeansKeep` it is 94.0 million.

`liveness` checks `NothingLeft` under `FairSpec`: every step of a command is taken in the end, a lock that keeps becoming free is taken, a sweep finds each folder old enough in the end, lock files age, sweeps keep coming, and the TLC of a killed tlaup ends (since 2026-11-20). Its model is small on purpose: one process that starts runs, one that sweeps and cleans, one run id, no symmetry. A model with two run ids (1.3 million states) was tried and stopped after 35 minutes inside the liveness check, with no answer.

**What `windows` showed** (2026-11-20, finding K1-8). As first written it expected `KeptSurvives` and `CheckpointSurvives` to hold on Windows too. TLC's trace (23 states): a run that asked to be kept is killed while its TLC runs on, and on Windows its lock is free; a resume (`-recover`) into that folder takes the lock, stops before starting a TLC of its own (an error or a signal), and settles while the folder has no checkpoint yet, so it decides to delete it; the orphan TLC then commits a checkpoint and, a moment later, is ended by the lifeline; and the resume's end step deletes the folder, the fresh checkpoint with it. A first attempt to state a weaker property, "unless an orphan TLC works in the folder at the deletion", failed the same way, because the orphan had already ended when the folder went: the decision was made inside the window and carried out after it. So this is the window `windows-delete` shows, with a kept checkpoint as its cost, and no rule at the end step can see it. On Linux and macOS it cannot happen: the resume cannot take the lock while the orphan holds it. On Windows it needs a forced kill, a resume started within about two seconds of it, and that resume stopping before its own TLC starts; D15 accepts it, and [R6](../docs/design/11-runner.md#r6-run-folders) names it. `windows` now checks the properties that hold there, and `windows-checkpoint` shows this one.

## ToolStore

**Models.** Two or three tlaup processes and an upstream that publishes new bytes under a name at any moment. Install: look at upstream and the store, lock a `.tmp/` folder, make it, download, take the store lock, add (or find the same name and bytes there and discard), pin if nothing is pinned, release. Upgrade: the same, then move the pin if it named the build that was compared, and remove that build. Uninstall: take the lock, rename the build into `.tmp/`, delete it there, clear the pin if it named it. Pin. A reader: read the pin, look the build up, then Java opens the jar, with no lock. Any command can give up at the download or at a busy lock, and a tlaup can be killed anywhere, which leaves its `.tmp/` folders for the next mutation's cleanup.

`ReadUnderLock` chooses where a mutation reads what it decides on: under the lock, which is the fixed design, or before it, which the first wording allowed (K2-1). `UnpinFirst` is the option of K2-2 the maintainer did not take (decision D50).

**Leaves out.**

- Folder names. A build is a name and a version of its bytes, and an id stands for exactly one build; the `-2` suffix rule and two names that give one id text are not modelled. So "a reader never opens another build than the pin named" is true here by construction, and `NoDuplicate` only says that no action adds a second copy.
- The lock files under `.tmp/` as files. A `.tmp/` folder is locked or not; whether removing such a lock file is safe is the question `RunFolders` answers, and V11 now uses its rule (K2-4).
- `--force` and repair in place, `tool list`, the lookup cache, everything about the network except "what upstream publishes now".
- Half-written folders. `NoPartialBuild` says that only the two renames change what is in the store; that each is one rename is the design's claim, not something TLC can see.
- More than one SIGKILL in a behaviour.

**Properties.** `PinConsistent`, `NoPartialBuild`, `ReaderOutcome`, `NoDuplicate`, `TmpOwnerSafe` and `PinNeverMovesSilently`, as [03 lists them](../docs/design/03-run-stages-and-specs.md#k2-tools-store). Added: `PinWritesInstalled` and `InstallPinsInstalled` (what is pinned is installed at that moment), `TmpLockedWhileThere`, `ReaderChecked`, and `PinConsistentAfterKill`, which is `PinConsistent` without its exception.

**Results.** Constants not named are those of `ToolStore.cfg`: two processes, two names, two versions of each name's bytes, one SIGKILL, `ReadUnderLock` and `CheckInstalled` on, `UnpinFirst` off. Since the review (FC3, FC4) `Add` counts copies and `PinConsistent` excuses only the pin a killed uninstall left, which made the main model 6.9 million distinct states (4.6 before).

## Signals

**Models.** One tlaup process: it enters `signals_held`, looks at `Signals.first`, starts the child, attaches it, waits, sees it gone, prints the summary, leaves and exits. Up to three signals arrive at any of those moments, each SIGINT, SIGTERM, SIGHUP or SIGQUIT. Chosen at the start, in every combination: which of the four were ignored when tlaup started; whether SIGINT is left to the child (`tlaup repl`); whether the child ends by itself or only when killed; and, since 2026-11-20, whether the run is parsed. The process loop can fail (a closed pipe), and the grace period can run out. Since 2026-11-20 (D51, D52): tlaup can die at any moment (`TlaupDies`: SIGKILL or a crash), after which no handler runs and the lifeline ends the child (`LifelineEnds`, fair unless `Lifeline` is off); and in a parsed run, while the child runs, the parser can see a checkpoint start and end (`CheckpointBegin`, `CheckpointEnd`, the second fair), and with `Defer` a first signal between the two is held and sent on at the end.

**Leaves out.**

- Installing the handlers is one step, and so is restoring them. A signal between two `signal.signal` calls is not modelled.
- What the terminal does: a Ctrl-C that reaches the child as well is the child ending at a moment of its own.
- The reader threads, the queue, output. A main thread blocked in a write (the risk G3 names).
- More than one child; Windows. (SIGKILL of tlaup was left out until 2026-11-20.)
- Where a signal from the terminal is delivered. The model delivers every signal to tlaup. Since D60 (2026-11-20, review finding TU1) that is exact for a parsed run on Linux and macOS, whose JVM has a process group of its own, so a terminal's Ctrl-C reaches tlaup alone; before D60 it also reached the JVM, which the model could only show as "the child ending at a moment of its own", and `FirstSignalWaitsForCheckpoint` held while the commonest real case broke it. In a raw run and the REPL the child shares tlaup's group and a terminal's signal reaches both, which is still "the child ending at a moment of its own"; no deferral applies there. SIGQUIT, which tlaup forwards to the JVM of a parsed run, changes no state and is not modelled as forwarded.
- A stop for a closed stdout (D58; review finding FC9): the launcher stops the child as for a first signal, outside `Signals`. G3 says how it combines with signals (it is not one, a later signal kills, the first stop's code wins); the model does not have it.
- Where in the pipe the parser's checkpoint mark is: the model takes the mark as what tlaup sees. Late, the child may already be past the commit when 2196 is read, which only makes the wait longer. Early, which is the side that matters (review finding FC8): TLC has printed 2195 and begun writing `.tmp` files, the line is still in the pipe or the queue, and a first signal arrives and is sent on at once, breaking the checkpoint. The completeness test then drops it, so the cost is a lost checkpoint, not a wrong result; G3 says so too.

**Properties.** `NoDefaultHandler`, `ChildNeverOrphaned`, `ExitCode`, `IgnoredStaysIgnored` and `NothingStartsAfterSignal`, as [03 lists them](../docs/design/03-run-stages-and-specs.md#k3-signals). `ExitCode` and `NothingStartsAfterSignal` do not hold as first worded (K3-1, K3-2); what holds in their place is `SignalNeverLost`, `ExitCodeAsSeen`, `LateSignalChangesNothing`, `NothingStartsAfterSeenSignal` and `SignalReachesChild`. Added: `SecondSignalKills`, `LeftAloneNotRecorded`, `IgnoredChangesNothing`, and one liveness property, `Stops`: once a signal is recorded, tlaup exits, whatever the child does. `NoDefaultHandler` is true by the shape of the model, since entering installs every handler in one step. Added 2026-11-20: `ChildEndsWithTlaup` (liveness: once tlaup is killed the child ends in the end) and `FirstSignalWaitsForCheckpoint` (a first signal does not stop the child while a checkpoint is being written); `SignalReachesChild` is reworded to allow the held signal, and `Stops` counts a killed tlaup as gone.

## The stateful tests

**Brought up to the revision of 2026-11-20** the same day, after the maintainer settled the three open points. What each machine gained, what it could not mirror (the kill of tlaup is a test of its own, not a rule; `RunLock`'s second look; `UnlinkOnRelease`), and how the machines did on broken models is in [design 03](../docs/design/03-run-stages-and-specs.md#specs-and-their-tests). The table and the paragraphs below are from 2026-11-18 except where they say otherwise. With the CI profile the three machines against their throwaway models took 44, 32 and 17 seconds on 2026-11-20, and the whole folder, with the plain tests, 98 seconds.

`tests/stateful/` has one Hypothesis `RuleBasedStateMachine` per spec, as [03 describes](../docs/design/03-run-stages-and-specs.md#specs-and-their-tests). They call the step functions named in [11 R6](../docs/design/11-runner.md#r6-run-folders), [12 V1](../docs/design/12-tools-and-downloads.md#v1-version-store) and [20 G3](../docs/design/20-groundwork.md#g3-java-launcher). All three exist now (G3's from work package 21, V1's from 27a, R6's from 35a), and no stateful test carries the `pending` marker any more.

Each file also has a plain test with a second Python process. For the two that use locks it confirms that a lock object in the test process is refused, and refuses, exactly as another process is. For the signals it confirms that a signal from outside is recorded as one the process sends itself, and that the handler has run when `os.kill` returns.

**Run against a throwaway model: yes.** Each machine was also run against a small model of its step functions kept beside it (`reference_rundirs.py`, `reference_store.py`, `reference_launcher.py`): real `filelock` locks, real files, real signal handlers and a real child, with none of the product round them. Those runs are the tests named `..._reference_model`; they are not `pending`. All pass with the 200 examples of the CI profile, which took about 95, 75 and 26 seconds for the three machines on a machine that was also running TLC; with the 50 of the development profile, about 10, 14 and 3 seconds. The work package that builds the real code deletes the throwaway model with its tests. The signals machine now runs against `tlaup.java.launcher` (work package 21), and `reference_launcher.py` and its tests are gone. The store machine now runs against `tlaup.versioning` (work package 27a), and `reference_store.py` and its tests are gone. The run-folder machine now runs against `tlaup.tlc.rundirs` (work package 35a), and `reference_rundirs.py` and its tests are gone.

**The machines were tried on broken models.** A machine that cannot fail proves nothing, so each throwaway model was broken on purpose in several ways, one at a time, and the machine run with 200 examples: twenty-two broken models in all, each tried twice, with shrinking switched off. The signals machine caught all seven of its own both times. The run-folder machine caught six of seven, then four of seven: it always finds a lock that is not held or not taken, and it missed at least once a kept folder removed too early by the sweep, by `cache clean` or at the end of a resumed run, each of which is a rule of one step that R6's unit tests cover with an injected clock. The store machine caught four of eight both times: it finds a cleanup that ignores locks, a removal that is not a rename, and an upgrade that moves the pin or removes a build it should not; both times it missed the four mistakes of reading before the lock (K2-1 and K2-5), although earlier runs of the same machine had caught two of them, and one such run is how K2-5 was found. The four replay tests catch those four every time (tried). The broken models and these runs were scratch work and are not in the repository. The first version of the machines caught under half of the broken models. What changed that: a start-up phase that leaves earlier runs or installs behind, made with the same step functions; one kill per example, as in the specs' models; a stubborn child that notes the SIGTERM it gets; and, for the signals, drawing the phase before which no signal arrives. What it shows about the limits: a race that needs one command to wait while another takes four steps is found by chance or not at all. That is why the counterexamples of K2-1 and K2-5 are also plain tests that replay their steps. After decision D49 the run-folder machine and its throwaway model were changed to the new `cache clean` rule and run again: it passes with the 200 examples of the CI profile (77 seconds). With the old rule put back in the throwaway model, the new check caught it in one of two runs of 50 examples; it was not tried with 200.

**How to run them.** `hypothesis` is a development dependency ([01 T10](../docs/design/01-testing.md#t10-coverage-policy-and-pytest-settings)), and `uv run poe test` runs the three files with the rest; this runs them alone:

```bash
uv run pytest tests/stateful --no-cov
```

`CI=1` gives the 200 examples of the CI profile. No stateful test is `pending` any more.

## What was not checked

- The specs say what one agent understood of the design, and no second reader has compared them with the sections. K2-5 shows the kind of gap that leaves: the first store spec was wrong in the design's favour, and TLC was content.
- The bounds: two processes for most results (three for configs with one run id), two run ids (three for one config with one process), two names with two versions each, one SIGKILL, three signals. A flaw that needs more is not found. Run ids are never reused, so the number of run ids bounds the number of runs in a behaviour: with two, one run and one resume (review finding FC2). `RunFolders-one-process-three-ids` reaches a folder resumed twice, or a resume resumed; two or three processes with three run ids were not run. `liveness` has one run id, so `NothingLeft` is not checked with `-recover`.
- Liveness for the run folders in the small model only.
- Anything inside one step: the two system calls of a rename, a folder half deleted, a handler half installed.
- Windows and macOS. Network file systems, where `flock` may not hold. The Windows variants of `RunFolders` switch the inherited lock off on POSIX files; they are not a model of Windows.
- The lifeline agent and the inherited lock themselves: the specs assume that the agent ends the JVM and that the JVM's duplicate keeps the lock; research 33 and 35 tried both, and R6's and G3's unit tests pin them.
- The stateful tests against real code: all three machines now run against it (work packages 21, 27a and 35a). Whether a machine catches a mistake in the real step functions is known only from the broken throwaway models.
- The step functions' signatures were not tried against the rest of the design beyond reading it; a worker may find that one needs another argument.
