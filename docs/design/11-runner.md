# 11. Milestone 1: the runner

Covers milestone 1's runner items, "Reaching TLC", the preflight, and two of the problems the roadmap records without a solution. Relies on decisions D9, D24, D29, D34, D35, D36, D45, D51 to D54, D58 and research [13](../research/13-override-loading.md), [15](../research/15-exit-codes-and-signals.md), [16](../research/16-config-path.md), [17](../research/17-metadir.md), and the top-up results [19](../research/19-workers-auto.md), [20](../research/20-metadir-creation.md), [21](../research/21-output-encoding.md), [24](../research/24-path-flags-and-links.md), [25](../research/25-default-checkpoints.md), [28](../research/28-java-11-and-macos-java.md), [31](../research/31-progress-and-closed-stdout.md), [33](../research/33-inherited-lock.md), [34](../research/34-metadir-write-frequency.md) and [35](../research/35-jvm-ends-with-tlaup.md), worked in on 2026-11-20. Built on the invocation value and the launcher of [20](20-groundwork.md).

```python
# tlaup/tlc/runner.py
@dataclass(frozen=True)
class RunOutcome:
    result: RunResult | None          # 10 P3; None for a raw run, where nothing is parsed
    exit_code: int                    # what tlaup exits with (02 X1)
    tool_exit_code: int | None
    stopped_by: str | None            # "int", "term", "hup"
    stderr_tail: tuple[str, ...]
    warnings: tuple[str, ...]         # the preflight's warnings (R7, J2, J3), for the JSON reporter of milestone 4
    run_folder_kept: Path | None      # R6; the run folder that was kept (the recovered one after -recover)
    resume_command: str | None        # R6; set when run_folder_kept is
    dropped_checkpoint: str | None    # R6; "not-asked", "incomplete" or "depth-first" when a checkpoint was not kept
    stopped_for_closed_pipe: bool     # R1; the reader of stdout went away and TLC was stopped (D58)

def run_tlc(inv: TlcInvocation, java_inv: JavaInvocation, reporter: Reporter, *,
            paths: AppPaths, now, notice: Callable[[str], None]) -> RunOutcome
def run_tlc_raw(inv: TlcInvocation, java_inv: JavaInvocation, *, paths: AppPaths, now,
                notice: Callable[[str], None]) -> RunOutcome
```

Both functions have the same frame, and only the middle differs:

```python
with signals_held() as signals, run_folder(inv, paths, now) as folder:  # 20 G3, R6
    try:
        if folder.kept_summary.count:
            notice(reminder(folder.kept_summary))  # R6, "Kept folders are visible"
        reporter.start(run_info)  # run_tlc only; the last thing before the child
        process = run_streaming(..., on_held=...) or run_passthrough(
            ...
        )  # the middle; starts nothing if a signal came first;
        # on_held hands the waiting line to reporter.notice (R2)
        settled = folder.settle(process)  # R6: decided before anything is printed
        outcome = RunOutcome(...)
        reporter.finish(outcome)  # run_tlc only
    except BaseException as error:
        settled = folder.settle(None)  # R6: the first decision stands if there is one
        if settled.kept:
            error.add_note(...)  # R6, "The note"
        raise
    finally:
        reporter.close()  # run_tlc only; 22 O1
# leaving the block deletes or keeps the folder, releases the lock, restores the handlers
if reporter.write_error:  # run_tlc only; 22 O1: close() never raises
    if settled.kept:
        reporter.write_error.add_note(...)  # R6, "The note": the outcome is lost, the note is not
    raise reporter.write_error
return outcome
```

Three things the frame fixes in place:

- **`reporter.start` is called once, after the run folder is entered and immediately before the child is started.** Nothing that can fail for an ordinary reason (the lock, the folder, `run.json`, the sweep) happens after it, so the live layout ([22 O4](22-reporters.md#o4-live-display)) is never opened for a run that then cannot start.
- **`reporter.close()` runs in a `finally` inside the frame.** `close` is the reporter's own way out: it leaves the live layout and copies the text it held back to stdout, is safe to call twice, and is safe when `start` was never reached ([22 O1](22-reporters.md#o1-reporter-interface)). After a normal run it has nothing left to do. It never raises: a write that fails inside it (a closed pipe) is kept in `reporter.write_error`, and `run_tlc` raises that after the frame when nothing else is passing, so the pipe still ends in 141. Raising it loses the outcome, and with it the command's `print_run_notes`; so when the folder was kept, the same two note lines are first added to the write error with `add_note`, as the `except` branch does for any other error, and the handler prints them on stderr (R6). A kept folder is announced on every way out of the frame. When the middle raises, it runs before the exception leaves `run_tlc`, so the `error:` line the application's handler prints afterwards is written to the ordinary screen and the output that was shown before the failure is still printed (D9).
- **Neither the runner nor the reporter prints the "Checkpoint kept" note.** The outcome carries it and the command prints it after the run function has returned; an exception carries it as a note (R6).

## R1 Run errors reported as what they are

Roadmap: "Today every `OSError` during a run, including a broken pipe from `--raw | head`, becomes \"'java' not found\"."

**Problem.** `tlc/runner.py:217` and `:265` catch `(SubprocessError, OSError)` around the whole run and raise `FileNotFoundError("'java' not found")`.

**Design.** The catch-all goes. Each failure has its own place:

| What happens | Where it is caught | Result |
| --- | --- | --- |
| `java` is not on the system | The preflight ([13 J2](13-modules-and-java.md#j2-finding-java)), before the run | `JavaNotFound`, code 3 |
| The executable cannot be started (`FileNotFoundError`, `PermissionError`, other `OSError` from `Popen`) | The launcher | `ToolStartError`, code 5, with the path and the operating system's message |
| tlaup's own stdout is closed (`BrokenPipeError` while printing) | The application's error handler ([14 F10](14-config-and-cli.md#f10-no-tracebacks)), after the launcher's `finally` has stopped the child and emptied its queue ([20 G3](20-groundwork.md#g3-java-launcher)), the reporter has been closed and the run folder has been settled | Exit 141, no message ([02 X1](02-cross-cutting.md#x1-exit-codes)) |
| The run folder cannot be created or locked | `run_folder` (R6) | `FileOperationError`, code 5 |
| Anything else | The application's error handler | `internal error`, code 5 |

The `BrokenPipeError` reaches the handler only because tlaup prints through consoles of its own class: a plain Rich console catches the error itself and exits 1 ([14 F6](14-config-and-cli.md#f6-messages) has the class, X1 the rule and what was tried). Everything the runner and the reporters print goes through those consoles.

**A closed stdout stops TLC** (decision D58, top-up; [research 31](../research/31-progress-and-closed-stdout.md)). The JVM does not stop when its stdout's reader goes: it ignores SIGPIPE, `System.out` swallows the error, and TLC runs to its end unseen, on Linux, macOS and Windows alike. Nobody can read the result of such a run, so tlaup stops it, by the same path as a first signal, in a parsed and in a raw run:

- *Parsed run.* tlaup's own write to stdout fails with `BrokenPipeError`, the launcher's `finally` terminates the child and empties its queue (G3), and the run exits 141; the table above has it. A clean run in plain mode writes nearly nothing to stdout until its result, so `run_streaming` also asks `reader_gone(1)` at each turn of its loop and stops the child when the reader has gone (review finding TU2, [20 G3](20-groundwork.md#g3-java-launcher)); without that, `tlaup tlc Spec | head` on a long clean run would run TLC to its end unseen.
- *Raw run.* tlaup writes nothing to stdout itself, so `--raw | head` gives the closed pipe to TLC, not to tlaup. `run_passthrough` waits for the child in steps of a fifth of a second; in each step it asks whether tlaup's stdout is a pipe whose reader has gone (`reader_gone(1)`, which [14 F10](14-config-and-cli.md#f10-no-tracebacks) already has). If so it terminates the child as for a first signal, the grace period and the second step (`kill()`) follow as for a signal, and the run exits 141 with no message. The outcome records `stopped_for_closed_pipe`, and the run folder is settled as for an interrupted run.
- *Windows.* `select.poll` does not exist there, so `reader_gone` cannot see the closed pipe and a raw run cannot either: TLC runs on, as it does without tlaup. The help of `--raw` says so in one line. A parsed run on Windows stops as on the other systems, through the `EINVAL` rule of D57 (X1).

Why a raw run too, although tlaup otherwise does not touch its streams: a model check nobody can see can hold every core for hours, and raw and parsed runs then answer alike. The cost is a poll every fifth of a second on a descriptor, in a loop that already wakes that often.

**Rejected.** Keeping one catch and inspecting the exception inside it: the place an error is raised is what says what it means, and a single catch loses that. Reporting a closed pipe as an error: `head` closing the pipe is the user's intent, and 141 with no message is what other tools do.

**Tests.** Feature, real process with a real pipe, Linux and macOS: `tlaup tlc --raw Spec | <a reader that takes one line and exits>`, with a fake `java` that prints a line and then a line a second for a minute: tlaup exits 141 within a few seconds and the fake has received SIGTERM. Unit, on `run_passthrough`, with `reader_gone` injected false (the Windows case): the child runs to its end. Unit, on the launcher ([20 G3](20-groundwork.md#g3-java-launcher)): a path that does not exist and a file without the execute bit each raise `ToolStartError`, code 5, with the path and the system's message ("permission" for the second). These are unit tests because the command line cannot reach them: a `java` that is missing or not executable is never found, so `tlaup tlc` answers `JavaNotFound`, code 3, and the in-process scenario of `tlc_errors.feature` for "a `java` on `PATH` that is not executable" asserts exactly that. Feature, real process with a real pipe (it cannot be shown in-process, where there is no pipe to close): tlaup's stdout is piped to a reader that takes one line and exits, the fake `java` prints 100,000 lines and then waits; tlaup exits 141 within a few seconds, stderr has no traceback, and the fake has exited. The line count is ten times the launcher's queue bound on purpose: with exactly the bound the test would pass even if a full queue could hang tlaup (G3).

**Changelog.** Fixed: "Errors while running TLC were all reported as \"'java' not found\". Each is now reported as what it is." Changed: "When the program reading tlaup's output goes away (`tlaup tlc --raw Spec | head`), TLC is stopped instead of running on unseen; not on Windows for `--raw`."

**Depends on.** G2, G3, F6, F10. **Risks.** The 141 path held on every Typer from 0.22.0 to 0.29.2 and every Rich from 13.8.0 to 15.0.0, on Linux and macOS ([research 23](../research/23-typer-versions.md), [research 30](../research/30-library-behaviours.md)); the newest-dependencies job guards later versions. Python may print "Exception ignored ... BrokenPipeError" at interpreter exit unless stdout is pointed at the null device first, which F10's handler does. A raw run that stops TLC for a closed pipe reacts within a fifth of a second plus TLC's own exit.

## R2 Signals

Roadmap: "Forward SIGTERM to the JVM so a CI timeout does not leave TLC running; exit 130 on Ctrl-C; survive a second Ctrl-C while draining output."

**Problem.** Today the only signal handling is `except KeyboardInterrupt`. SIGTERM is not an exception, so tlaup dies and the JVM lives on; a second Ctrl-C escapes the drain loop.

**Facts (research 15, run twice).** SIGTERM to tlaup kills tlaup and leaves the JVM running under PID 1. One Ctrl-C ends with 143, or 130, depending on a race. A second Ctrl-C ends silently with 130 through Typer. TLC prints nothing when signalled. The JVM exits in under a second after a signal.

**Design.** The mechanism is the launcher's ([20 G3](20-groundwork.md#g3-java-launcher)): handlers instead of exceptions; first signal terminates the child, a second kills it, the loop drains until the pipes close. What the runner adds:

- **The handlers are held for the whole run**, by the `signals_held()` block shown at the top of this document: from before the run folder is made and the child is started, through the process loop, until `reporter.finish` has printed the summary, the reporter has been closed and the run folder has been deleted or kept. A signal that was already ignored when tlaup started stays ignored, and SIGQUIT is survived so the JVM can print a thread dump (G3). A second Ctrl-C that arrives after the JVM has gone, which is the usual case since the JVM exits within a second, is recorded and changes nothing: the summary is printed in full.
- **A signal before the child exists** (while the run folder is being made) is recorded; the runner starts nothing, cleans up the folder and exits with that signal's code.
- After the loop, if a signal stopped the run, `result.status` becomes `INTERRUPTED`; the SANY diagnostics and any error and trace already parsed are in the result as usual.
- The exit code is 130 for SIGINT, 143 for SIGTERM, 129 for SIGHUP, set by tlaup.
- The run folder is settled as R6 says: an interrupted run's folder is kept if the run asked to be kept and the folder holds a complete checkpoint (D52, D53).
- **The terminal's signals reach tlaup alone in a parsed run** (decision D60, settled 2026-11-20 from review finding TU1). On Linux and macOS the JVM of a parsed run is started in a process group of its own ([20 G3](20-groundwork.md#g3-java-launcher)), so a Ctrl-C, a closed terminal or a Ctrl-\ reaches only tlaup, which acts on it as G3's table says and forwards SIGQUIT so that the thread dump still comes. Before D60 the JVM shared tlaup's group, so a Ctrl-C typed at the terminal reached TLC directly and the deferral below held only signals sent to tlaup alone. Raw runs, the REPL, `sany` and `pcal` keep the child in tlaup's group, since the child talks to the terminal there; a terminal Ctrl-C then reaches both, as before. A tlaup that hangs is stopped by a second Ctrl-C, which its handler turns into `kill()` of TLC, or, if tlaup is killed, by the lifeline. Windows is unchanged (D15).
- **A first signal while TLC writes a checkpoint waits** (decision D52, top-up). In a parsed run the runner tells the launcher when the parser sees 2195 and 2196 (`Signals.checkpointing`, [20 G3](20-groundwork.md#g3-java-launcher)); a first signal between the two is recorded at once and sent to TLC when the checkpoint is written, with one line that names the signal, so the wait is not mistaken for an ignored signal: `waiting for TLC to finish writing its checkpoint; press Ctrl-C again to stop now` after Ctrl-C, and `SIGTERM received: waiting for TLC to finish writing its checkpoint; send it again to stop now` for SIGTERM (SIGHUP likewise). A second signal kills at once, as before. Research 35 found that a stop in the middle of a checkpoint, tlaup's own SIGTERM included, can leave a checkpoint that fails to recover or recovers with exit 0 and misses states; this keeps tlaup's own first signal from doing that. It applies to the first signal of each kind tlaup acts on (SIGINT, SIGTERM, SIGHUP), as every other rule of G3 does; so a CI timeout's SIGTERM waits as well, for as long as the CI system waits before its SIGKILL. With D60 a Ctrl-C typed at the terminal is held too, in a parsed run on Linux and macOS. "While TLC writes" means from the moment tlaup has read 2195: a signal that comes while that line is still in the pipe is sent on at once (review finding FC8). The line goes through the reporter, not through `ui`, since the reporter is between `start` and `close` then ([14 F6](14-config-and-cli.md#f6-messages)): the launcher hands it to the runner's `on_held` hook on the main thread ([20 G3](20-groundwork.md#g3-java-launcher)), and the runner gives it to `reporter.notice` ([22 O1](22-reporters.md#o1-reporter-interface)). The plain reporter writes it on stderr at once; the live display shows it in its Status panel and copies it to stderr when it closes, so it is still on the terminal after the layout is gone ([22 O4](22-reporters.md#o4-live-display)). A raw run holds no signal for a checkpoint and has no such line. (Stage 4 review, 2026-11-24: the waiting line goes through the reporter, question Q12.)
- **A tlaup killed with SIGKILL**, or one that crashes past its handlers, runs none of this. The lifeline in the JVM ends TLC within about two seconds (decision D51, [R6](#r6-run-folders) "A killed tlaup", [20 G3](20-groundwork.md#g3-java-launcher)); the run folder is settled by the next sweep.
- **Raw runs** use `run_passthrough(..., forward_interrupt=True)`: all three signals are forwarded to TLC and the exit codes are the same. There is no checkpoint deferral, because tlaup reads none of TLC's messages in a raw run. Nothing is printed to stdout by tlaup; the "Checkpoint kept" note, if any, is printed on stderr by the command, as for a parsed run (R6).

**Rejected.** Handlers scoped to the process loop: loses the summary to a quick second Ctrl-C (G3 has the reasoning). Leaving Ctrl-C to the terminal in raw mode: a SIGINT sent to tlaup alone, as a CI system does, would then not reach TLC.

**Tests.** `tlc_signals.feature`, six scenarios with real processes (tlaup started with `sys.executable -m tlaup`; the signal is sent to the tlaup process only): SIGTERM, one SIGINT, two SIGINTs, each in parsed and raw mode. Assertions: the exit code; that the fake `java` exited; and, in parsed mode, that stdout holds what was printed before the signal plus an "interrupted" line. The two cases that depend on the exact moment a signal arrives cannot be arranged from outside the process and are plain pytest tests that drive `run_tlc` and send the signal from a reporter callback ([20 G3](20-groundwork.md#g3-java-launcher), Tests): a SIGTERM before the child is started (the fake `java` log stays empty, code 143, no run folder left), and a second SIGINT during the summary. Integration: the same six with the real JVM. Feature, real processes on a pseudo-terminal (D60): `press Ctrl-C` in a parsed run reaches tlaup and not the fake `java`, which is in a group of its own, and in a raw run reaches both; the scenario is G3's. The checkpoint deferral is in R6's real-process tests (a fake that prints 2195 and 2196 around a pause), and the lifeline in R6's integration test (tlaup killed with SIGKILL; no `java` left).

**Changelog.** With G3.

**Depends on.** G3, R6. **Risks.** Not run on macOS or with a real terminal (research 15 lists both as untested); the macOS CI job runs the signal scenarios. A checkpoint that takes minutes holds a first Ctrl-C for minutes; the line on stderr says how to stop at once.

## R3 Non-UTF-8 output

Roadmap: "Do not crash on non-UTF-8 bytes in TLC output."

**Problem.** `Popen(..., text=True)` decodes with the locale's encoding and raises `UnicodeDecodeError` on a byte that does not fit; printing a character the terminal's encoding lacks raises `UnicodeEncodeError`.

**Facts (top-up, [research 21](../research/21-output-encoding.md)).** TLC, SANY and the translator write exactly what the JVM's stream encodings produce, which the JVM derives from the locale of its own process: UTF-8 under a UTF-8 locale, US-ASCII with one `?` per character it cannot represent under `C` or `POSIX` (Linux CI often runs there), cp1252 on Windows, UTF-8 on macOS. The `?` cannot be undone. On v1.7.4 with Java 11 under a C locale TLC also reads a UTF-8 spec wrongly, and the PlusCal translator writes `?` into the comments of the user's own `.tla`. `-Dfile.encoding=UTF-8 -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8` fixed every case tried, on Java 11, 21 and 25, both builds, Linux, macOS and Windows. No JVM option fixes a non-ASCII spec or cfg *path* under a C locale: rolling dies with `InvalidPathException`, v1.7.4 looks for a file of `?`s.

**Design.** The launcher always passes the three encoding options, so TLC's output is UTF-8 on every system and locale (decision D56, [20 G3](20-groundwork.md#g3-java-launcher)). It still reads bytes and decodes each line as UTF-8 with `errors="replace"`, the guard for what the options do not reach (a user's own `JAVA_TOOL_OPTIONS`, a jar of another vendor); with `--raw` nothing is decoded at all. For a spec or cfg path with a character outside ASCII while the locale tlaup runs under is not UTF-8, the preflight adds a warning with a hint (`hint: TLC cannot open a file whose name has non-ASCII characters under the C locale; run with LC_ALL=C.UTF-8`); tlaup does not change the child's environment itself. When tlaup writes to a stream whose encoding cannot represent a character, the two consoles are created with `errors="replace"` on the underlying stream (`sys.stdout.reconfigure(errors="replace")` at start), so printing cannot raise either; this also closes the milestone 4 point "no crash when the output encoding cannot represent a glyph".

**Rejected.** Decoding with the locale's encoding: once the launcher passes the options, what TLC writes no longer follows the locale. The first design said here that TLC's output does not follow the locale tlaup sees in any way that was checked; research 21 corrected that: without the options it follows the JVM's own locale-derived encoding, which is the locale the child inherits. `surrogateescape`: keeps the bytes but produces strings Rich and JSON cannot print. Setting `LC_ALL=C.UTF-8` in the child's environment when the locale is C or POSIX: it would fix non-ASCII file names, but it changes the child's environment behind the user's back, and `C.UTF-8` is missing on some systems; a hint leaves the choice to the user.

**Tests.** Feature, in-process: the fake `java` replays a file containing the bytes `FF FE` and a Latin-1 `é` inside a trace; the scenario asserts the exit code and that the surrounding lines are intact. Feature, real process (the variable is read when the interpreter starts, so it has no effect in-process): tlaup started with `PYTHONIOENCODING=ascii` and a trace holding `é` exits with the run's code and no traceback. Unit, the preflight: a spec path with `é` under `LC_ALL=C` (injected) gives the warning; the same under `C.UTF-8` does not. Integration: a spec whose trace holds `é` and `日`, run with `LC_ALL=C` on both builds, prints both characters (the options work); the same through `tlaup pcal` leaves a non-ASCII comment in the `.tla` byte for byte.

**Changelog.** With G3. Added: "A hint when a spec or cfg name has non-ASCII characters and the locale is not UTF-8, which TLC cannot open."

**Depends on.** G3. **Risks.** A replaced character in a trace value is shown as U+FFFD, so the value printed is not the value TLC computed; the line is otherwise intact. With the options this happens only when something outside tlaup overrides them. A spec saved in Latin-1 is now read as UTF-8 on Java 11, as Java 18 and later read it anyway.

## R4 Spec, cfg and working folder

Roadmap: "Pass a `--cfg` file outside the project root to TLC so that TLC reads the file that was validated; today only its name is passed." Decision D34.

Row labels in this section (B6, D3, E2, F12 and so on) are the rows of research 16's tables, not items of these design documents.

**Problem (research 16, real runs).** `resolve_cfg_file` validates the right file and then passes TLC only its name unless it is under the project root. TLC then read a *different* file of the same name (rows F5, F7, F8, F12) or none (F11, F13, F14). tlaup and TLC also search in different orders. Separately: with a relative spec path that has a folder part, TLC ignores `-DTLA-Library` (E3, E4), and a file in the working folder shadows the module beside the spec (D3).

**Design.**

1. **tlaup does not change folder.** TLC runs where tlaup was started.
2. **The spec is passed as an absolute path.** TLC then takes the spec's folder as its own base folder: modules beside the spec are found (D6), `-DTLA-Library` is honoured (E2), and nothing in the working folder can shadow them. The default cfg is `Spec.cfg` beside the spec (B1).
3. **Symbolic links in the spec's path are not resolved.** The path is made absolute as the user gave it, so TLC looks for modules beside the path the user named, not beside the link's target. `..` is removed textually (`os.path.abspath`, which fixes row F10) when the result is the same file (`os.path.samefile`), which it always is unless a `..` follows a link; otherwise the path is passed with its `..` in place. TLC never resolves links: it builds paths from the spec path as given and hands them to the operating system, so modules and the default cfg are found beside the path the user named, also for a spec that is itself a link to a file ([research 24](../research/24-path-flags-and-links.md), rows F1 to F5, Linux, macOS and Windows). **On Windows** (top-up) the operating system collapses `..` as text before it follows a link, so a path with its `..` in place after a link reaches another file or none (research 24, point 4: a spec path `link/../proj/Spec.tla` that works on Linux and macOS was not found on the Windows runner). There tlaup passes the textual form only when it names the same file as the path the user typed, which by Windows' own reading it does, and reports `SpecNotFound` otherwise.
4. **The cfg tlaup validated is the cfg TLC gets**, written relative to the spec's folder. The relative path is computed from the resolved forms of both, `os.path.relpath(realpath(cfg), realpath(spec.parent))`, because the operating system follows links when it walks `..`; computed this way the path names the validated file with or without links, provided TLC joins it to the spec's folder and lets the operating system walk it. The preflight computes it and stores the text (`TlcInvocation.config_arg`), so the function that builds the command reads no disk ([20 G1](20-groundwork.md#g1-tlc-invocation)). Rows B2, B3, B5 and B8 show a relative `-config` is read against the spec's folder on both builds, including with spaces, and B4 shows `..` works for a cfg under the spec's folder. An absolute `-config` would also work on rolling but fails on v1.7.4 when the spec is absolute too and the cfg is outside the spec's folder (B6, B9), so it is not used. On Windows, when spec and cfg are on different drives, `relpath` raises and the absolute path is passed; from rows B6 and B9 that should fail on v1.7.4.

   **Checked by research 24** (top-up). A cfg outside the spec's folder reached with `..` from an absolute spec is read on v1.7.4 and rolling (`../out.cfg`, `../other/o.cfg`, `../../outside/o.cfg`). With the spec's folder behind a symbolic link, TLC hands the joined path to the operating system unchanged, and the `relpath` of the resolved forms named the validated file in all ten layouts tried, on Linux and macOS, both builds. **On Windows** the same computation is wrong when a link is involved, because Windows collapses `..` as text (research 24, second CI run: the resolved form missed in 4 of 8 rows, the lexical form read the validated file in 8 of 8). So on Windows the relative value is computed from the paths as typed, `os.path.relpath(os.path.abspath(cfg), os.path.abspath(spec.parent))`, with no `realpath`, which is also what Windows' own file opening validates. The function takes the platform as an argument, so both forms are unit-tested on Linux (D15: no Windows CI).
5. **How `--cfg` is found** (unchanged order, roadmap "Keep"): if absolute, that file; otherwise beside the spec, then in the working folder, then in the project root, which the preflight finds from the spec immediately before this step (R11). In each place only a name ending in `.cfg` is tried: `--cfg foo` looks for `foo.cfg`, never for a file named `foo`. TLC strips a trailing `.cfg` from `-config` and adds it again (research 16, source notes), so a file without the suffix could be validated by tlaup and then not be the file TLC opens. The first that exists wins. `CfgNotFound` lists the paths tried.
6. **With no `--cfg`, tlaup checks nothing.** TLC looks for `Spec.cfg` beside the spec and reports its absence itself (255 on v1.7.4, 151 on rolling, research 15). tlaup does not pre-check the default, because rolling builds can also take the configuration from inside the spec, a path research 16 lists as untested, and a check could refuse a spec TLC accepts.

**What changes for users.** TLC used to run in the project root, or the spec's folder; it now runs where tlaup was started. A TLA+ module lying loose in the project root, outside `modules/`, was found only because TLC ran there; it is no longer found. Where a relative path among TLC's own arguments resolves is TLC's rule, not tlaup's:

- `-config` (when given to TLC directly instead of through `--cfg`): against the spec's folder, not the working folder (row B2).
- Every other path-taking flag: against the folder tlaup was started in, on both builds ([research 24](../research/24-path-flags-and-links.md)): `-dump`, `-metadir`, `-userFile`, `-recover`, `-simulate file=`, and on rolling `-dumpTrace`, `-loadTrace` and `-teSpecOutDir`. No other flag takes a path. `-dump` and `-userFile` need their folder to exist (TLC exits 1 before checking anything otherwise); `-dumpTrace` creates it. TLC's own help for `-dumpTrace` says "relative to the same directory as the main spec", which is wrong with the absolute spec tlaup passes, and is not copied into tlaup's help. So the help and the changelog promise the rule: "relative paths after `--` are read from the folder you run tlaup in; `-config` is read from the spec's folder"; the help still advises absolute paths.

**Rejected.** Running in the spec's folder with the bare name: the most tested arrangement and independent of where tlaup is started, but the maintainer chose the invoking folder (D34). Keeping the project root: keeps both defects unless the spec is made absolute anyway, at which point the root buys only the loose-module lookup. Resolving links in the spec's path: TLC would then search beside the link's target, and a spec linked into a project would lose the project's modules (research 24 confirmed that TLC searches beside the path it is given, F1 to F3). Accepting a cfg name without `.cfg` as typed: see step 5.

**Tests.** Unit, on `resolve_spec`, `resolve_cfg` and the preflight's `config_arg` with real files in a temporary tree shaped like research 16's layout: for each of rows F1 to F14 the `-config` value, when joined to the spec's folder, is the same file (`samefile`) as the one validated; the same with the spec's folder reached through a symbolic link, including a cfg outside it reached with `..` (research 24's rows R1 to R10); with the platform given as Windows, the lexical `relpath` and the textual spec rule, with expected values written out by hand from research 24's Windows rows; `--cfg foo` with a file `foo` and no `foo.cfg` is `CfgNotFound`. Feature, in-process: `--cfg ../outside/out.cfg` with a decoy `out.cfg` in the project root; the logged Java command names the outside file. Integration: the same with real TLC on both builds, asserting the constant value TLC printed, including research 24's link rows on Linux and macOS (skipped where links cannot be made).

**Changelog.** Fixed: "`--cfg` pointing at a file outside the project could make TLC read a different file with the same name." Breaking: "TLC now runs in the folder where `tlaup` was started (was the project root, or the spec's folder). TLA+ modules in the project root but outside `modules/` are no longer found; move them beside the spec or into `modules/`. A relative `-config` given after `--` is read relative to the spec's folder, as TLC does with an absolute spec path; use `--cfg` instead. Every other relative path after `--` (`-dump`, `-userFile`, `-dumpTrace` and the rest) is read from the folder you run tlaup in. `--cfg NAME` looks only for a file ending in `.cfg`."

**Depends on.** G1. **Risks.** A spec that reads files by relative path through a Java module now depends on where tlaup is started, as it does with plain Java. The Windows cross-drive case is inferred, not run; the Windows rules of steps 3 and 4 were checked on a GitHub-hosted runner, not by tlaup's own CI (D15).

## R5 Spec names

Roadmap: "A dot in the name is mangled by `with_suffix` (`Foo.v2` becomes `Foo.tla`), `.` raises an error, and any existing file such as a `.cfg` is accepted as the spec."

**Problem.** `resolve_spec_file` builds the candidate with `with_suffix(".tla")`, which replaces whatever follows the last dot; it accepts any path that exists; and `.` reaches `with_suffix` and raises `ValueError`.

**Design.** `resolve_spec(text: str, cwd: Path) -> Path`:

1. Empty, `.` or `..`: `UsageError` ("SPEC must be a TLA+ file or its name").
   A trailing path separator is dropped first, so `Foo/` is read as `Foo` (settled while building 32, 2026-11-25, a low-impact choice by the stage 5 lead: a shell completes a folder name with one).
2. If `text` ends in `.tla`: that path must be a file.
3. Otherwise try, in order, `text + ".tla"` (appended, never replacing a suffix, so `Foo.v2` looks for `Foo.v2.tla`) and `<parent>/spec/<name>.tla` (the documented `spec/` layout).
4. A path that exists but does not end in `.tla` is never accepted: `tlaup tlc Spec.cfg` is `SpecNotFound` with the hint "did you mean Spec.tla?" when that exists. A folder is refused only here, when no candidate of step 3 exists: with both a folder `Foo/` and a file `Foo.tla`, `tlaup tlc Foo` runs `Foo.tla`; with only the folder it is a `UsageError` saying SPEC is a folder.
5. `SpecNotFound` carries the list of paths tried, printed as details (roadmap, error messages).

The result is absolute; links are not resolved (R4, step 3). The `spec` folder name is a constant ([14 F3](14-config-and-cli.md#f3-settings-that-go-and-settings-that-stay)).

**Rejected.** Accepting any existing file and letting TLC complain: TLC's message for `Spec.cfg` as a spec is a parse error in a file the user did not mean. Searching more folders than `spec/`: the search order would need documenting and nobody asked for it.

**Tests.** A parametrised unit test: `Foo`, `Foo.tla`, `Foo.v2`, `dir/Foo`, `Foo` found under `spec/`, `.`, `""`, `Foo.cfg`, a folder name alone, a folder name with a `.tla` file of the same name beside it. The seven cases of 0.8.x's `test_resolution_scenarios.py` are taken over as inputs of this test (inventory rows S1 to S4); the old file itself went with the old suite in package 03b (decision D62). (Stage 4 review, 2026-11-24: the old file is not kept or moved, finding E5.)

**Changelog.** Fixed: "A spec name containing a dot (`Foo.v2`) was looked up as `Foo.tla`; `tlaup tlc .` failed with a traceback; an existing file that is not a spec (such as `Spec.cfg`) was passed to TLC."

**Depends on.** G2. **Risks.** A user who relied on passing a spec file with another suffix can no longer do so; TLC itself requires `.tla`, so no working use is lost.

## R6 Run folders

Roadmap: "Stop run-cache cleanup from deleting other specs' directories ... TLC also adds a timestamped folder per run that is never removed; define when those are cleaned up." Also settles the recorded problem "The run-cache fingerprint covers the default `.cfg` only", and decision D36. Revised 2026-11-20 for the top-up answers (questions 24, 25, 30, 33, 34, 35) and decisions D51 to D53, which change D36 and D48 and narrow D49; the changes are marked "top-up".

**Facts (research 17).** TLC makes one timestamped folder under `-metadir` per run. It deletes that folder after a clean finish; after a violation (rolling builds), a signal or a crash it stays. Two v1.7.4 runs started in the same second in one `-metadir` collide and one fails. Deleting the folder of a running TLC makes it crash at the next checkpoint or queue spill. tlaup's cleanup matches `<stem>_` as a prefix, so running `Foo` deletes the folder of `Foo_bar`; `module add` and `remove` delete every run folder, including those of runs in progress. `-recover` needs the timestamped folder of a checkpointed run and reuses it. With `-checkpoint N` the folder holds `queue.chkpt`, `vars.chkpt` and others after the first interval. Rolling builds also write `<Spec>_TTrace_<n>.tla` and `.bin` beside the spec on every error.

**Facts (top-up).**

- *TLC checkpoints by itself* ([research 25](../research/25-default-checkpoints.md)). Without `-checkpoint`, both builds write a checkpoint every 30 minutes, counted from the JVM's start, in breadth-first and `-dfid` mode; `-simulate` never checkpoints; `-checkpoint 0` turns it off. A `-dfid` checkpoint holds the fingerprint set and no queue (read from the source, research 25), so it never holds `queue.chkpt` (see "Settle"). So every breadth-first run stopped more than about half an hour after it started has a checkpoint. The folder needed to resume is the whole timestamped folder, not the `*.chkpt` files alone: a run of hours leaves one to tens of gigabytes ([research 34](../research/34-metadir-write-frequency.md) measured 1.6 GB after 15 minutes of a fast run).
- *A checkpoint is not safe against a stop at the wrong moment* ([research 35](../research/35-jvm-ends-with-tlaup.md)). TLC writes `.tmp` files and then commits them one by one. Stopped in between, by any means, tlaup's own SIGTERM and Ctrl-C included, the folder either fails to recover or, in one window, recovers with exit 0 and silently misses states (1,534,282 of 1,771,561 on rolling). Every broken case left a `.tmp` file; no complete checkpoint did. Neither build registers a shutdown hook.
- *Resuming changes the counts.* Every recovered run in research 35 over-counted its distinct states by 0.1 to 1.7 %. The one recovery that repeated the run's `-seed` and `-fp` (research 25, rolling) gave the exact count, and rolling prints warning 2285 on every `-recover` that does not repeat them ([research 22](../research/22-more-tool-captures.md)). Both are random unless given; the start line (2187) names them on both builds ([research 19](../research/19-workers-auto.md)).
- *A killed tlaup* ([research 35](../research/35-jvm-ends-with-tlaup.md), [33](../research/33-inherited-lock.md), [34](../research/34-metadir-write-frequency.md)). Without help the JVM outlives a tlaup killed with SIGKILL, on every system. A small `-javaagent` that watches tlaup's process id ends it within about two seconds (the lifeline, [20 G3](20-groundwork.md#g3-java-launcher)). On Linux and macOS a `flock` belongs to the open file description, so a JVM started with a duplicate of the lock's descriptor keeps the lock held after tlaup is killed, until the JVM ends; on Windows a `filelock` lock does not follow the child. Nothing written under the folder for a long time does not mean no TLC runs there: a simulation never writes.

**Design.**

*One folder per run, for parsed and raw runs alike.* No per-spec folder, no fingerprint, no matching by name.

```
<cache>/runs/<run-id>.lock      held by tlaup for the whole run, and by its JVM (D51)
<cache>/runs/<run-id>/
    run.json      {"schema": 1, "spec": "<abs path>", "cfg": ..., "build": "rolling@bc1b506",
                   "pid": 12345, "started": "2026-11-15T10:00:00Z", "tlaup": "0.9.0",
                   "keep": false, "fp": 58, "seed": 8556987057680880581,
                   "ended": null, "kept": false, "size": null}
    <TLC's timestamped folder>
```

`run-id` is the UTC start time and eight random hex digits, `20261115T100000Z-3fa9c1d2`. `-metadir` is this folder. The lock file sits beside the folder, not in it, so the lock is taken before the folder exists and there is no moment when another tlaup can see an unlocked new folder. (Top-up: `no_keep` is replaced by `keep`, D53; `fp`, `seed` and `size` are new, D52 and D53.)

`RunRecord` below is what `tlaup cache` lists for one folder (its id, the fields of `run.json`, its size, whether its checkpoint is complete, when it last changed, whether its lock is held). It is not the `RunInfo` a reporter is given at the start of a run ([22 O1](22-reporters.md#o1-reporter-interface)).


**Formal check, 2026-11-18.** This section was written as `specs/RunFolders.tla` and checked with TLC; [the specs' README](../../specs/README.md#runfolders) says what was modelled, with which bounds, and what was found. What the check changed here is marked "formal check". Of the two points it left to the maintainer, one was settled on 2026-11-18: `cache clean` spares the checkpoint of a killed run unless `--all` is given (decision D49, below under `cache clean`). The other, what a SIGKILL reaches, was settled on 2026-11-20 (decision D51, under "A killed tlaup"). Settled on 2026-11-18, from the agent feedback of the check ([feedback](../feedback/2026-11-18-tla-tools-as-an-agent.md), point 5): a run stopped with no intent to resume leaves nothing (decision D48); on 2026-11-20 decision D53 made that the default. The spec was revised for D51 to D53 and checked again on 2026-11-20.

*The steps, one call each* (decision D46; fixed by the checked spec). `run_folder` is the steps of `RunStart` in order and then `entered()`; leaving the block is the four end steps of `RunFolder`; `sweep` and `clean_runs` are loops over `list_entries` and `EntryVisit`. The steps are the spec's actions, and the stateful test calls them one at a time from several objects in one process, each holding its own locks ([03](03-run-stages-and-specs.md#specs-and-their-tests)). They take the runs folder and the fields of `run.json` instead of the invocation, so the test needs neither; `wait=0` makes one attempt.

```python
# tlaup/tlc/rundirs.py, under run_folder, sweep and clean_runs
def list_entries(runs: Path, *, folders_only: bool = False) -> list[str]   # the run ids that have a folder or a lock file

class RunLock:                                              # tlaup's own lock on one <id>.lock (top-up, D51)
    def __init__(self, path: Path, *, wait: float): ...
    def acquire(self) -> None                               # FileOperationError after `wait`
    def duplicate(self) -> int                              # os.dup of the locked descriptor, for pass_fds
    def release(self) -> None                               # unlock, then close
    def abandon(self) -> None                               # close without unlocking (see "A killed tlaup")

class RunStart:                                             # "Start"
    def __init__(self, runs: Path, now, *, run_id: str | None = None, recover: Path | None = None,
                 info: Mapping[str, object] | None = None, wait: float = 5.0): ...
    run_id: str
    path: Path
    def create_lock_file(self) -> None
    def take_lock(self) -> None                             # RunLock.acquire; FileOperationError after `wait`
    def take_recover_lock(self) -> None                     # nothing to do unless `recover` lies under an existing runs/<id>/
    def make_folder(self) -> None
    def write_run_json(self) -> None
    def sweep(self) -> KeptSummary
    def entered(self) -> RunFolder                          # hands the locks to the folder; also after a failed step
    def abandon(self) -> None                               # every lock descriptor closed, nothing unlocked: a kill

class RunFolder:                                            # as above, and "End"
    def end_own(self) -> None                               # delete the folder and remove its lock file, unless it is kept
    def release_own(self) -> None
    def end_recovered(self) -> None                         # the same for the folder -recover named
    def release_recovered(self) -> None
    def abandon(self) -> None                               # RunLock.abandon for both locks (see "A killed tlaup")

class EntryVisit:                                           # one entry of runs/ under its lock
    def __init__(self, runs: Path, run_id: str, now): ...
    def take_lock(self) -> bool                             # one attempt, no waiting; False: the entry is in use
    def sweep(self) -> None                                 # the sweep's rule for this entry
    def clean(self, *, include_kept: bool) -> bool          # `cache clean`'s rule; True if the folder went
    def release(self) -> None
```

*The locks* (top-up, D51). A run's own lock and the lock of the folder `-recover` names are tlaup's own: `RunLock` opens the lock file with `os.open` (read and write, create, never truncate, so the file's modification time is set only when it is created) and locks the descriptor with `filelock.lock_descriptor`, the library's documented lock on a descriptor its caller owns ([research 33](../research/33-inherited-lock.md)). That route, not `FileLock`, because only a descriptor tlaup owns can be handed to the JVM and later closed without unlocking; `FileLock` has no way to give its descriptor up without the unlock, and its `on_acquired` hook lends the descriptor on terms that do not cover passing it to a child. So tlaup writes the two things `FileLock` would have done:

- **The wait.** One non-blocking attempt every 50 milliseconds until `wait` is over, then `FileOperationError`, code 5.
- **The second look.** Once the descriptor is locked, `RunLock` compares it (`os.fstat`) with the file now at the path (`os.stat`): if the path is missing or names another file (device and inode differ), it unlocks, closes and starts over. This is the re-check the formal check found the protocol needs (finding K1-2), stated by file identity rather than by link count; the unit test under Tests pins it.

The visits of the sweep and of `cache clean` hold their lock only for the instant they look, never hand it to a child, and keep `filelock.FileLock` with one attempt (`timeout=0`). Two rules hold for every lock in this section (research 30): a lock is taken and released in one thread, since `FileLock` objects are thread-local; and `take_lock` never maps `filelock`'s `RuntimeError("Deadlock ...")` to "busy". That error comes only from a wait with no timeout, which nothing here uses; if it appears it is a bug and is reported as an internal error.

- **Start**, in this order: create the lock file and take its lock, waiting up to five seconds; if TLC's arguments hold `-recover PATH` and `PATH` lies under another run folder that exists, take that folder's lock too, the same way (see below); create the folder; write `run.json`; then `sweep`. The wait is there because a sweep or a `cache clean` of another tlaup may hold any lock for the instant it takes to look at the entry. A lock that cannot be had in five seconds is `FileOperationError`, code 5 (R1).
- **Keeping is asked for at the start** (decision D53, top-up). `tlaup tlc --keep`, the setting `tlc.keep` (default `false`) or `TLAUP_TLC_KEEP` marks a run as one whose checkpoint should survive an interruption; `run.json` records `"keep"`. Without it a run deletes its run folder at its end however it ended, checkpoint or not. A run that resumes, with `-recover`, from a folder whose `run.json` says `"keep": true` is a kept run too, since a kept folder is removed only when a resume from it finishes. When settle keeps a folder it writes `"keep": true` into its `run.json` as well as `"kept": true`, and a resume of a folder that says either is a kept run (review finding FC1): a folder whose own run did not ask, but which a later resume with `--keep` kept, would otherwise lose its checkpoint to a third resume without `--keep`. Asking at the start, not at the moment of the Ctrl-C, keeps D23 (no new prompts) and works the same in CI, in raw runs and after a kill, where nobody can be asked. `--no-keep` (D48) goes: not keeping is the default; a `tlc.keep: true` in the settings is overridden for one run with `TLAUP_TLC_KEEP=false`. Why: research 25 found that every breadth-first run stopped after half an hour has a checkpoint, of up to gigabytes; keeping each one by default, for 30 days, was a cost nobody chose, and the maintainer ruled that keeping must be asked for ([notes](top-up-notes-2026-11-20.md), [review](top-up-review-2026-11-20.md#to-redesign-later-kept-run-folders)).
- **The fingerprint and the seed** (decision D52, top-up). When TLC's arguments hold no `-fp`, tlaup passes `-fp <n>` with `n` chosen at random from TLC's own range (an index into its table of fingerprint polynomials, 0 to 130: `tlc2.util.FP64.Polys` has 131 entries on the rolling build; v1.7.4 is assumed the same and its integration test checks that the value is accepted); when they hold no `-seed`, tlaup passes `-seed <n>` with a random 64-bit integer. Each is decided on its own, so a user's `-fp` stays and tlaup adds only the seed. Both values go into `run.json` and into the resume command. When `-recover` names a folder under `runs/` whose `run.json` has them and the user gave neither, tlaup passes those instead of new ones, so a hand-typed resume repeats them too. Chosen by tlaup rather than read from the start line (2187) because that works for raw runs as well, where nothing is parsed. It is what TLC does anyway, random values, except that tlaup knows them.
- **Settle** (called by the runner after the process loop and before anything is printed, so the outcome and the summary can say what happened): the folder is **kept** when all three hold (top-up: conditions 2 and 3 replace "something under the folder is named `*.chkpt`" and "not started with `--no-keep`"):
  1. the run did not finish: a signal stopped it, or tlaup itself is failing (an exception is passing through, `process` is `None`), or TLC's exit code is neither 0 nor one of its violation codes 10 to 14 (research 15);
  2. the run asked to be kept (D53);
  3. the folder holds a **complete checkpoint** (D52): TLC's timestamped folder holds `queue.chkpt` and `vars.chkpt`, and no file under it ends in `.tmp` or is named `settings.tmp.chkpt` (rolling's settings file during a checkpoint, which the old test "named `*.chkpt`" matched with nothing to recover). `complete_checkpoint` is that test, and the sweep and `cache clean` use the same one.

  Anything else is deleted at the end. A run that finished, with or without a violation, has nothing to resume (research 17: with `-checkpoint` TLC leaves checkpoint files after a violation). A folder whose checkpoint is not complete is treated as one with no checkpoint, not kept with a warning: a resume from it either fails or, in one case research 35 found, reports "no error" without exploring the whole state space, and offering a command that can lie is worse than offering none. The loss is small: a few interrupted checkpoints that would have recovered are deleted, because tlaup cannot tell them from the broken ones. `settle` returns a `Settled`: the `Kept`, or, when a checkpoint was there and was not kept, why (`"not-asked"`: complete, but the run did not ask; `"incomplete"`: the run asked, but the checkpoint was not complete; `"depth-first"`: the run asked, and it was a `-dfid` run, read from TLC's arguments, whose checkpoint holds no queue and so can never be resumed; review finding TU7). When the folder is kept, `run.json` gets `ended`, `"kept": true`, `"keep": true` (FC1) and `size`. `settle` decides once: a second call returns the first answer. The frame calls it again when an exception passes, and a run that had already finished when the exception came (a closed pipe while the summary was printed) stays "finished".

  **A checkpoint thrown away is said, in a few words** (D53). The outcome carries `Settled.dropped`. In a parsed run the terminal reporter adds it to the result line ("interrupted; a checkpoint was not kept (use --keep to keep one)", "...; the checkpoint was incomplete, nothing to resume", or "...; a -dfid run cannot be resumed"); in a raw run `print_run_notes` prints the same words on stderr as one line. So a user who wanted the checkpoint learns how to keep one next time.

  **What D48 said, now.** A trial run that is stopped and tried again smaller leaves nothing, without a flag: that is the default. A run that a time or state budget stops, if a budget is added later (it is not on the roadmap; feedback proposal 1), is settled as a run that finished: a budget is the user saying in advance where the run ends.
- **End** (leaving the block, also after a signal or an error): a kept folder is left and its lock released; any other folder is deleted, the lock file removed while the lock is still held, and the lock released. Removing the lock file is the last thing a process does under that lock. From then on its lock is on a file that has no name, another tlaup may already hold the lock of a new file under the same name, and the only step left is the release; the same holds for the sweep and for `cache clean`. If deleting the folder fails, the lock file is removed all the same, and a later sweep finds the folder with a free lock. (Formal check, 2026-11-18: the lock property as first worded did not allow for the instant between the removal and the release, [finding K1-1](../../specs/README.md#findings).) The end steps run only after the launcher has seen the child gone, which its `finally` guarantees on every way out ([20 G3](20-groundwork.md#g3-java-launcher)); see "A killed tlaup" for why that is now a rule. On Windows, where an open file cannot be deleted, the removal under the lock fails and is ignored, and `RunLock` removes the lock file after it has unlocked and closed it, the order `filelock` uses there; another holder keeps its own handle open without delete sharing, so no other holder's file is removed ([research 30](../research/30-library-behaviours.md)).
- **The note.** For a kept folder the user is told on stderr:

  ```
  Checkpoint kept (2.1 GB, interrupted after 2 h 13 min, checkpoint of 14:02): <the run folder>
  Resume with: tlaup tlc <absolute spec> --cfg <absolute cfg> --keep ... -- ... -fp 58 -seed 8556987057680880581 -recover <TLC's timestamped folder in it>
  ```

  The duration is written by `format_elapsed`, the same function as the result line's ([22 O2](22-reporters.md#o2-delete-dead-display-code)). (Stage 4 sign-off, 2026-11-24: one duration form, settled with the maintainer at the stage 4 sign-off, 2026-11-24.)

  The first line names what `tlaup cache list` lists and `tlaup cache clean <run-id>` or `--all` removes, with its size and the reason it was kept, so the cost is seen the moment it is incurred (top-up, D53). "interrupted" is the reason for a signal; "tlaup failed" and "TLC crashed (exit N)" are the other two. The second line names the folder TLC needs, the one under it that holds the `*.chkpt` files.

  One function builds the two lines from a `Kept`, and there are two ways they reach the user, neither of which is the runner or a reporter printing:
  - A run function that returns puts them in the outcome (`run_folder_kept`, `resume_command`), and the command prints them with `print_run_notes(outcome, ui)`, the same call for a parsed and a raw run ([20 G1](20-groundwork.md#g1-tlc-invocation)). `reporter.finish(outcome)` receives the same outcome, so the JSON reporter of milestone 4 can put the folder in its result; the terminal reporter prints nothing about it ([22 O3](22-reporters.md#o3-terminal-reporter)).
  - A run function that is left by an exception has no outcome to return. The frame adds the two lines to the exception with `add_note`, and the application's handler prints an exception's notes on stderr after its `error:` line, or alone when the exception is a closed pipe ([20 G2](20-groundwork.md#g2-domain-errors), [14 F10](14-config-and-cli.md#f10-no-tracebacks)). So a folder kept because tlaup itself failed is announced as well.
- **Kept folders are visible** (D53, top-up). `tlaup cache list` shows each kept folder, and each unsettled folder that is resumable, with its spec, cfg, build, size, age, why it was kept and whether its lock is held ([23 C1](23-command-layout.md#c1-command-tree)). Every `tlaup tlc` start prints one line on stderr while kept folders exist: `3 kept run folders hold 7.4 GB (tlaup cache list)`. It comes from the sweep of that start (`RunFolder.kept_summary`), using the `size` that `run.json` recorded at the keep and measuring a folder that has none; the frame prints it through the command's `Ui` after the run folder is entered and before `reporter.start`, so it stands above the run's own output, in the scrollback after a full-screen run too. That line is the answer for folders the user has forgotten or is unsure about: they are reminded at every run until they decide. `--show-command` and the `cache` commands do not print it.
- **The resume command** is built from the whole request ([20 G1](20-groundwork.md#g1-tlc-invocation), `TlcInvocation.request`) and the resolved paths, never from the text the user typed:
  - `tlaup tlc`, then the spec as the absolute path the preflight resolved, then `--cfg` with the absolute path of the validated file when `--cfg` was given. Absolute, so the command finds the same two files from any folder (research 17: recovery needs the same spec and cfg).
  - `--keep`, since a resumed run that is interrupted again should be kept again (top-up).
  - Each option the request carried, in a fixed order: `--workers` (see below), `--coverage`, `--raw`, each `--java-opt=VALUE`. `--auto-install` is left out: the build is installed.
  - `--workers`: the number TLC reported in its start line (2187) when the run was parsed and TLC's arguments held no `-workers`, because rolling's settings check compares the worker count too (warning 2285, research 22); otherwise as given on the command line, and not at all when the value came from the settings.
  - `--`, then TLC's arguments as given, with every `-recover`, `-fp` and `-seed` and the word after each taken out, then `-fp` and `-seed` with the run's values from `run.json`, then `-recover` and `Kept.checkpoint_dir`. A run that was itself started with `-recover PATH` therefore prints one `-recover`, naming `PATH`, which is where TLC went on writing.
  - Joined with `shlex.join` (`subprocess.list2cmdline` on Windows, as R9).

  What it does not carry: the environment (`TLAUP_JAVA_OPTS`, `TLAUP_CONFIG`) and the folder the run was started in. A relative path among TLC's own arguments (`-dump out.dot`) means the same only when the command is run from the folder the first run was started in, since TLC reads every relative path but `-config` against its working folder (R4); the spec and the cfg do not depend on it. The build is whatever is pinned when the command is run; `run.json` records the build the checkpoint was written by, and `tlaup cache list` shows it.

  **A resumed run's counts** (D54, top-up). TLC prints 2197 and 2198 when it recovers, and the result is marked `resumed` ([10 P3](10-parser.md#p3-result-model)). Its state counts are shown as approximate unless the run was resumed with the original `-fp` and `-seed`: tlaup knows that when `-recover` names a folder under `runs/` whose `run.json` has the values this run passed. The resume command always passes them. When a resumed run is kept in the recovered folder, settle also records `-fp` and `-seed`: a value equal to the recorded one stays, and a different one (or one where none was recorded) is written as null, so a checkpoint that holds fingerprints of two values never counts as an exact resume later (settled while building 35b, 2026-11-25, a low-impact choice by the stage 5 lead).
- **Why keep checkpoints, when asked.** An interrupted run can be resumed only from that folder (research 17: `-recover` worked on both builds). Research 25 answered how often a folder holds one: every breadth-first run stopped after about half an hour, at sizes of up to tens of gigabytes. That is why keeping is now asked for (D53) and kept folders are visible, rather than kept by default for 30 days.
- **The first Ctrl-C waits for a checkpoint being written** (D52, top-up). In a parsed run the parser sees 2195 ("Checkpointing of run ...") and 2196 ("Checkpointing completed ..."); a first signal that arrives between the two is recorded and held, and is sent to TLC when 2196 arrives. tlaup says that it is waiting for TLC to finish writing its checkpoint and that a second Ctrl-C stops at once (the line, and where it is shown, are [R2](#r2-signals)'s); a second signal kills at once, as before. The mechanism is the launcher's ([20 G3](20-groundwork.md#g3-java-launcher)); the runner tells it from the parser's events. On Linux and macOS this holds a Ctrl-C typed at the terminal too, since the JVM of a parsed run has a process group of its own (D60). In a raw run tlaup reads nothing, and the completeness test of "Settle" is the only protection; a SIGKILL, a crash or a second Ctrl-C can still stop TLC in the middle of a checkpoint, and the same test catches the result.
- **`sweep`** looks at each entry of `<cache>/runs/` whose lock it can take at once; an entry whose lock is held belongs to a live run, or to the TLC of a killed one (D51), and is never touched, and that includes the locks its own process holds (a second lock object on the same file in one process is refused like any other, tried with the locked `filelock`). Taking an entry's lock creates its lock file when there is none, because the lock library opens the file with "create". So a sweep or a `cache clean` that listed an entry just before its run ended, or that meets a folder with no lock file, leaves a new, empty lock file behind; the lock-file rule below removes it an hour later (formal check, 2026-11-18). The rules (top-up, D53; the first wording removed kept folders after 30 days and unsettled ones after a day):
  - A kept folder is never removed by the sweep, whatever its age and whatever it holds. It goes only when a resume from it finishes, by `tlaup cache clean --all`, or by `tlaup cache clean <run-id>`.
  - A folder with a `run.json` that was never settled (its tlaup was killed, or crashed past its handlers) is settled by the sweep the way its run would have been: spared as kept if its `run.json` says `"keep": true` and it holds a complete checkpoint (D49), otherwise removed at once, whatever its age. At once is safe because a free lock means no TLC runs there (see "A killed tlaup"); it was one day while a free lock could hide an orphan TLC.
  - A folder with no `run.json` was not made by the runner (see R9: a command pasted from `--show-command`). It is removed 30 days after its last change, which is the newest modification time of anything under it ([research 34](../research/34-metadir-write-frequency.md): the timestamped folder's own time does not move while files grow). Such a folder has no lock of tlaup's, so its age is the only guard; a pasted simulation that writes nothing for 30 days is not protected, and R9's help says to give a pasted long run a `-metadir` of the user's own.
  - A lock file whose folder is gone is removed only when the file is more than one hour old, and while the sweep holds its lock. The age matters: a run that is starting has made its lock file and not yet its folder, and between making the file and locking it there is an instant in which a sweep can take the lock first. A file that young is left alone, and the starting run gets the lock a moment later through its five-second wait. The age is the file's modification time, which creating the file sets and taking or releasing the lock does not change: `RunLock` never truncates, and `filelock` changes it on locking before 4.2.1 ([research 30](../research/30-library-behaviours.md); the lower bound is [30 B2](30-ci-and-release.md#b2-build-fixes)). On Windows lock files do not outlive their release, so this rule has almost nothing to do there, harmlessly.

  The age of the newest change under a folder is also what `tlaup cache list` shows as "stopped" for an unsettled folder, whose `ended` is empty: when the run stopped, not whether a TLC still runs there (research 34; option 2 below is rejected as a test of that). Errors while deleting are ignored, and the next sweep tries again (on Windows a file that is open cannot be deleted). Two sweeps are never in one folder at once: each holds the entry's lock. (The first wording gave "another sweep may be deleting the same folder" as the reason; corrected by the formal check, 2026-11-18.)
- **`-recover PATH` among TLC's arguments**: TLC resumes in the folder `PATH` names and writes its checkpoints there, not in the new run's folder. A relative `PATH` is resolved against the folder tlaup was started in, as TLC reads it ([research 24](../research/24-path-flags-and-links.md)), before anything below is decided. If `PATH`, with links resolved as far as it exists, lies under `<cache>/runs/<id>/` and that run folder exists, three rules apply, whether or not `PATH` itself exists: a `-recover <cache>/runs/<id>/states` whose `states/` is missing still takes the folder's lock. Taking it costs nothing, and the folder is protected while TLC decides what to make of the path; the run-folder machine of the formal check (`take_recover_lock`) asks for exactly this.
  1. The old run's lock, `<cache>/runs/<id>.lock`, is taken at the start, after the new run's own lock and before the sweep (see "Start"), and held to the end. No sweep, this run's own or another tlaup's, can then remove the folder while TLC works in it.
  2. If that lock is not free after the five-second wait, another tlaup is running in that folder or resuming from it, or the TLC of a killed tlaup is still ending there, and two TLCs writing one checkpoint would destroy it. The run stops before anything is started: `FileOperationError`, code 5, "the run folder <path> is in use by another tlaup run". With D51 this is exact on Linux and macOS: the formal check's finding K1-3 (a second TLC on one checkpoint) cannot happen there.
  3. At the end the old folder is settled by the same rule as any other, with the checkpoint looked for in it and `keep` taken from this run, which is a kept run when the old one asked or was kept (see "Keeping is asked for at the start"): deleted if the resumed run finished, kept (with a fresh `ended` and `size`, and the same note) if it was interrupted again with a complete checkpoint, deleted with the "incomplete" words if its checkpoint was broken. The new run's own folder holds no checkpoint and is deleted.

  A `PATH` outside `<cache>/runs/`, or under a `runs/<id>/` that has no folder, is TLC's to judge; tlaup takes no second lock, settles only its own run folder, and prints no note for a folder it does not manage.
- **`-metadir` among TLC's arguments**: the user's wins; `run_folder` makes no folder and no lock of its own and cleans nothing in the user's folder. The signal handling is the same, and so are `-fp` and `-seed`; with no `run.json` of tlaup's, a resume by hand has to repeat them, and rolling's warning 2285 names them. **With `-recover PATH` as well**, the three `-recover` rules above still apply whenever `PATH` lies under an existing `<cache>/runs/<id>/`: that folder's lock is taken and held for the run, and the folder is settled at the end. They key on where `PATH` points, not on whether tlaup made a folder for this run; without this a sweep could delete the recovered folder under TLC.
- `module add` and `module remove` no longer touch run folders. `tlc --cleanup` goes; `tlaup cache clean` replaces it ([23 C1](23-command-layout.md#c1-command-tree)). It takes each lock before it looks, as the sweep does, and removes a lock file with its folder:
  - by default it removes every run folder whose lock is free and that the sweep would remove: an unsettled folder that is not resumable. It never removes a kept folder, or an unsettled one that is resumable, or one with no `run.json`;
  - with `--all` it also removes the kept ones, the unsettled resumable ones, and those without a `run.json`;
  - with a run id (`tlaup cache clean <run-id>`, new, D53) it removes that one folder, whatever it is, when its lock is free; an id that names no folder is `NotFound`, code 4, and a held lock is `FileOperationError`, code 5, "in use".

  **Nothing that can be resumed is removed without `--all` or its id** (decision D49, settled 2026-11-18, [finding K1-4](../../specs/README.md#findings); narrowed by D53 to runs that asked to be kept). The first wording let `cache clean` and the sweep disagree about a folder that was never settled, because its tlaup was killed, and that holds a checkpoint: the sweep left it for 30 days, and `cache clean` removed it without `--all`, because its `run.json` says `"kept": false`. Now `cache clean` uses the sweep's rule. The other option, leaving `cache clean` as it was on the ground that no "Checkpoint kept" note was ever printed for such a folder, was not taken. In the spec this is `CleanSparesCheckpoint = TRUE`, and every property holds.

*What this settles.* The prefix-match deletion and the deletion of running runs cannot happen: nothing is deleted by name, and a held lock protects a live run, raw or parsed, and, on Linux and macOS, the TLC of a killed one. The v1.7.4 same-second collision cannot happen: no two runs share a `-metadir`. The fingerprint question disappears: there is no fingerprint, because nothing is reused between runs.

*Trace specs (D36).* On a build with the capability `no_generate_spec_te` ([00](00-overview.md#what-a-build-can-do)), tlaup adds `-noGenerateSpecTE`, unless TLC's arguments contain `-generateSpecTE`, `-noGenerateSpecTE` or `-teSpecOutDir`. v1.7.4 does not write these files and rejects the flag (research 17), so it is never passed there. D36's second half, which kept a run folder whenever an unfinished run had written a checkpoint, is replaced by D53.

*A killed tlaup* (decision D51, settled 2026-11-20; top-up). Before D51 a tlaup killed with SIGKILL left its JVM running and its lock free: a sweep or `cache clean` could delete the folder under it, and a `-recover` into it could start a second TLC on the same checkpoint (finding K1-3); the design accepted that and listed four options. Taken: **option 4 on every system, plus option 3 on Linux and macOS.**

- *Option 4, the lifeline* ([research 35](../research/35-jvm-ends-with-tlaup.md)). The launcher adds a small `-javaagent` to every JVM it starts; it watches tlaup's process id and ends the JVM within about two seconds of tlaup's death, however tlaup died, with `-Xrs` among the user's options and under the REPL too. The mechanism is in [20 G3](20-groundwork.md#g3-java-launcher). An orphan TLC serves no purpose: nobody reads its output, and it can hold every core for days.
- *Option 3, the inherited lock* ([research 33](../research/33-inherited-lock.md)). On Linux and macOS the JVM is started with duplicates of the run's lock descriptors in `pass_fds` (`RunFolder.lock_fds`: the run's own and, after `-recover` into a managed folder, the recovered folder's; `RunLock.duplicate`), so the locks stay held until the JVM is gone, not only until tlaup is. The launcher closes tlaup's duplicates once `Popen` has returned. With the lifeline alone the lock would be free for up to two seconds while TLC still runs; with both, "the lock is free" means exactly "no TLC runs here". So the sweep, `cache clean` and `-recover` rule 2 are right without an exception, and the sweep may remove an unsettled folder at once.
- *Rules the inherited lock brings.* A release in tlaup unlocks the JVM's copy too, since it is one open file description. So the lock is released, and the lock file removed, only after the launcher has seen the child gone, which the frame and the launcher's `finally` already guarantee on every way out. If a way out ever cannot confirm that, the end step closes the descriptor without unlocking (`RunLock.abandon`) and leaves the lock file, and the operating system releases the lock when the JVM ends. No `preexec_fn` anywhere in the launcher: with it, Python runs `filelock`'s at-fork hooks and `Popen` fails for a descriptor in `pass_fds` (research 33); the lifeline needs none.
- *Where only option 4 holds.* On Windows the lock does not follow the child (a byte-range lock belongs to the process), and on a network file system where `flock` is emulated by per-process locks neither does it. There the window of about two seconds after a kill remains, in which a `cache clean`, a sweep or a `-recover` can act on a live TLC; D15 accepts it, and the spec's Windows variant shows it.
- *Rejected.* Option 1, accepting the risk: it was only the fall-back until question 35 was answered. Option 2, counting an unsettled folder's age from its last write: not a test of liveness, since a simulation never writes and a long state or liveness check can be silent longer than any threshold (research 34); the last write is kept only to say when a stopped run stopped. Option 3 alone: an orphan TLC would then hold its folder for as long as it runs, possibly days, invisible. A duplicate taken in `FileLock`'s `on_acquired` hook instead of tlaup's own descriptor: it keeps `filelock`'s re-check for free, but passing a borrowed descriptor to a child is a use the hook's documentation does not cover; tlaup's own descriptor follows the documented API and puts the re-check in tlaup's tests. The other ways of ending the JVM research 35 tried (the parent-death signal, a pipe the agent waits on, a watcher process, a Windows job object): each works on fewer systems, or slows every JVM exit, or needs `preexec_fn`; [20 G3](20-groundwork.md#g3-java-launcher) has the list.

**Rejected.** *Keeping one folder per spec with an exact-name match and a pid file*: fixes the prefix bug but keeps the same-second collision on v1.7.4 and needs a rule for "the spec changed". *Always deleting at the end*: loses checkpoints a user asked for. *Keeping every folder that holds a checkpoint unless the user says otherwise* (the first wording with D48's `--no-keep`): research 25 makes that every run stopped after half an hour, at up to gigabytes for 30 days; replaced by D53. *Asking at the Ctrl-C whether to keep*: a new prompt (D23), and nobody can be asked in CI, in a raw run or after a kill. *Keeping a folder that did not ask until the end of the same tlaup's next run*: brings back the "unsure" folders D53 removes. *An expiry for kept folders* (30 days, or 7): a kept folder is something the user asked for, and the reminder at each run replaces a silent removal. *Keeping an incomplete checkpoint with a warning*: the resume can report "no error" having missed states. *Never deleting; a `cache clean` command only*: one large violation left 29 MB in the research run; folders would grow without limit. *A pid file instead of a lock*: pids are reused, and a lock is released by the operating system when the process dies. *The lock file inside the folder*: leaves a gap between making the folder and locking it. *A run folder for parsed runs only*: a raw run would get an unlocked folder that cleanup could delete under it, the defect this item removes. *Removing every lock file whose folder is gone* (the first revision): can remove the lock file of a run that is starting, after which a `cache clean` finds its folder unlocked. *The resume command "as typed"*: the typed words are gone once resolved, a relative spec breaks from another folder, and a run started with `-recover` would print the flag twice. *The reporter printing the note*: a raw run has no reporter, and a run that fails has no `finish`. *Reading `-fp` and `-seed` from TLC's start line instead of choosing them*: works for parsed runs only. *Passing `-checkpoint 0` by default*: the checkpoint is what a long interrupted run that asked to be kept needs.

Changed: "A first Ctrl-C while TLC is writing a checkpoint waits for the checkpoint to finish, also one typed at the terminal (Linux and macOS, not with `--raw`); a second stops at once." Changed: "On rolling builds tlaup passes `-noGenerateSpecTE`, so TLC no longer writes `_TTrace_` files next to the spec. Pass `-generateSpecTE` after `--` to get them." The entry for a killed tlaup is [G3](20-groundwork.md#g3-java-launcher)'s, and the one for `tlc --cleanup` is [C1](23-command-layout.md#c1-command-tree)'s. (Stage 4 review, 2026-11-24: `-recover` takes the folder's lock whenever the path lies under an existing run folder, also when the path itself is missing, question Q9; the real-process deferral scenario places its signal with the fake's checkpoint marker, and the fake commits before it prints 2196, question Q10; the waiting line is shown as R2 says; R6's entries for a killed tlaup and for `--cleanup` were dropped as duplicates of G3's and C1's, index "Clerical"; the fake waits for a release the step gives once tlaup shows the waiting line, and hangs only after 2196, finding E1, settled with the maintainer on 2026-11-24.)

**Depends on.** G1, G3 (the lifeline and `pass_fds`), F2, `filelock` (`lock_descriptor` for the run's locks, `FileLock` for the visits). **Risks.**

- On Windows and on network file systems a tlaup killed with SIGKILL leaves its TLC running for up to about two seconds with its lock free; a `cache clean`, a sweep or a `-recover` in that window acts on a live run (D51, D15). The spec found one more way this costs data there (finding K1-8): a resume started in that window that stops before its own TLC starts decides to delete the folder, the orphan TLC commits a checkpoint into it before it ends, and the resume's end step then deletes that checkpoint. No rule at the end step can see it, since the orphan has gone by then. It needs a forced kill, a resume within two seconds of it, and that resume failing at once; accepted with the rest of the window. It cannot happen on Linux and macOS.
- On Linux and macOS a lock stays held for up to about two seconds after its tlaup is killed. A second tlaup that needs it waits five seconds, which covers that.
- The completeness test of a checkpoint rests on research 35's breakpoints: every broken case left a `.tmp` file and no complete one did. A stop at a moment the research did not try could leave a broken checkpoint without one; liveness checking adds one more file to the commit and was not run. The deferral of the first Ctrl-C makes such a stop rarer in parsed runs; raw runs, crashes and kills are not covered by it.
- That the original `-fp` and `-seed` make a resumed run's counts exact rests on one run on rolling with one worker (research 25); the integration test above checks both builds and two workers, and until it passes the "approximate" mark is the honest default for every resumed run.
- A user who forgot `--keep` and interrupts a long run loses its checkpoint. The result line says so and names `--keep`, so it is a one-time lesson; keeping by default is what D53 ruled out.
- Kept folders can be large (gigabytes) and stay until the user removes them. The note, `tlaup cache list` and the reminder at every run make them visible; nothing removes them silently.
- `run.json` is read by the sweep for `keep`; a `run.json` that cannot be read is treated as no `run.json` (the 30-day rule), so a damaged kept folder is not lost at the next sweep.
- On Windows open files cannot be deleted; errors are ignored and the next sweep retries.
- Whether TLC writes its checkpoint files directly in the timestamped folder on every build was read from research 17's and 25's listings for the two supported builds only.
- The lock rules: `RunLock` is tlaup's own code, so its wait and its second look are tested by tlaup's unit tests above, not by a dependency's. The visits keep `FileLock`, and its behaviours were tried on every release on Linux and on eight releases on macOS and Windows (research 30): the second look arrived in 3.20.4; 3.20.4 to 3.29.4 also delete the lock file by name on release, which breaks mutual exclusion in a new way; 3.29.5 to 4.2.0 change the lock file's modification time when locking, which the one-hour rule reads; 4.2.1 is the first version where all of it holds. So the lower bound is `filelock>=4.2.1` ([30 B2](30-ci-and-release.md#b2-build-fixes)), and the spec checks the release-time unlink as a variant (`RunFolders-unlink-on-release`).

  The formal check (2026-11-18) modelled both answers about the second look ([results](../../specs/README.md#runfolders)). With a lock that looks again after it is taken, every safety property holds, and holds without the one-hour rule too. Without that second look a waiter can end up holding a lock on a file that is no longer at the name. Then, with three tlaups, two hold "the lock" of one name at once; and a run folder is deleted under a live TLC as soon as an hour passes while a run is starting (a suspended machine) or a folder deletion fails. So the second look is part of the protocol and not a detail of one version: `RunLock` has it, the bound gives it to the visits, and the unit tests under Tests pin both.
- The five-second wait for a lock is a guess at "longer than any sweep holds one, and than a killed tlaup's JVM takes to end".
- The resume command does not carry the environment or the starting folder, and uses whatever build is pinned when it is run (see "The resume command").

## R7 Override modules that do not load

Roadmap: "Report clearly when an override module fails to load." Decision D35.

**Facts (research 13, 35 cases per build, Java 25 only).** Most failures are silent: a class that is missing, not on the classpath, or not an `ITLCOverrides` gives no output and exit 0, and the plain TLA+ definition runs. v1.7.4 ignores the `tlc2.overrides.TLCOverrides` property and loads only a class with exactly that name, so a module whose class is named otherwise never loads there (checked with `docs/examples/QueueModule`). On rolling builds the property, when set, *replaces* the default: a real `tlc2.overrides.TLCOverrides` on the classpath is not loaded unless the property names it (case `prop_class_not_found`). A class that breaks while loading gives message 1000, exit 255, before any state is computed, without naming the class. A mismatch of module, operator or arity gives warnings 2402, 2403, 2400, but only if the annotation has `warn = true`. A successful load prints 2168, also only with `warn = true`.

So TLC's output can report only part of the failures. The rest must be checked by tlaup before the run.

**Design.** Four parts.

1. **Which classes are passed** (`tlaup/tlc/overrides.py`, part of resolving the invocation). Today's `get_override_classes` (`tlc/runner.py:85-109`) is replaced by:

   ```python
   @dataclass(frozen=True)
   class OverrideClass:
       name: str                    # "tlc2.overrides.QueueOverrides"
       declared_in: Path            # the classpath entry
       module: str | None           # the registered module's name, if the entry is one

   def collect_override_classes(classpath: Sequence[Path]) -> list[OverrideClass]
   ```

   For each classpath entry in order, folder or jar: the lines of its `META-INF/services/tlc2.overrides.ITLCOverrides` file, if it has one (comments and blank lines skipped). Then, for every entry that holds `tlc2/overrides/TLCOverrides.class` and whose service file did not already name it, the default name `tlc2.overrides.TLCOverrides`. Duplicates are dropped, first wins. `TlcInvocation.override_classes` is the list of names, and the property is passed only when the list is not empty.

   The second rule is the fallback today's code has for folders, kept and extended to jars. Without it a project's own `classes/tlc2/overrides/TLCOverrides.class`, or one inside a jar in `lib/`, would silently stop loading on a rolling build the moment any registered module made tlaup set the property.

2. **Before the run**:

   ```python
   def check_overrides(classes: Sequence[OverrideClass], classpath: Sequence[Path], build: Build) -> list[str]
   ```

   For each class:
   - If no classpath entry holds its `.class` file: warning "override class X (module M) is not on the classpath and will not load".
   - If the build lacks the capability `overrides_property` and the name is not `tlc2.overrides.TLCOverrides`: warning "TLC <build> loads Java overrides only from a class named tlc2.overrides.TLCOverrides; X (module M) will not load, and the TLA+ definitions of its operators will be used".
   - If two classpath entries hold a class named `tlc2.overrides.TLCOverrides`: warning that only the first is used.
   - If its `.class` file is found and does not implement `tlc2.overrides.ITLCOverrides`: warning "X (module M) is not an override class (it does not implement tlc2.overrides.ITLCOverrides) and TLC will ignore it". Research 13: TLC says nothing in this case and runs the TLA+ definitions. The file is read with the class-file reader of [13 M3](13-modules-and-java.md#m3-module-build-details), which gives the interface list exactly. A class that reaches the interface through a superclass is followed as far as the superclass can be found on the classpath outside the tools jar; when the chain leaves what can be read, or the file is not a readable class file, nothing is said. This row matters for names that come from a hand-written service file; a name that tlaup's own module build wrote was found by the same test.

   The warnings are returned in `TlcInvocation.warnings`; the command prints them on stderr before TLC starts and the run goes ahead (D35). They are copied to `RunOutcome.warnings` so the JSON reporter of milestone 4 can include them. `module add` runs the same check against the pinned build and prints the same warning at the moment the module is added.

3. **From TLC's output.** Message 2168 is parsed into `RunResult.overrides_loaded` ([10 P3](10-parser.md#p3-result-model)), one entry per override in the form `"<java_class>.<operator>"`. Warnings 2400, 2402, 2403 are ordinary warnings (severity 3) and are shown. The verbose header of the terminal reporter lists the loaded overrides.

4. **When TLC fails before starting.** If the result has an error of kind `exception` (message 1000) with no nested message of kind `config`, and the phase never reached `INITIAL_STATES`, and override classes were passed, the reporter adds one hint: "TLC failed while loading the spec. If the error comes from a Java override, one of these classes failed to load: ...". It is a hint, not a diagnosis: TLC does not name the class (research 13). The condition about the nested message is the reporter's, stated in [22 O3](22-reporters.md#o3-terminal-reporter): v1.7.4 reports a false `POSTCONDITION` with the same outer shape, and that capture has a nested configuration message, so the hint is not shown beside it.

   **A class compiled for a newer Java** (top-up, [research 28](../research/28-java-11-and-macos-java.md)). An override index class too new for the running Java is refused with message **2173**, severity 1, exit 255, not with 1000, so the hint above would stay silent for the commoner case. 2173 is an error of kind `exception` in the parser ([10 P5](10-parser.md#p5-error-traces)) and always gets a hint. Its text names the class and both class-file versions ("... has been compiled by a more recent version of the Java Runtime (class file version 69.0), this version of the Java Runtime only recognizes class file versions up to 55.0"); when it holds that sentence, the hint names them too: "the override class tlc2.overrides.TLCOverrides was compiled for Java 25 (class file 69) and TLC runs on Java 11 (up to 55); rebuild the module with `tlaup module add`, which compiles with `--release 11`, or run TLC on a newer Java". The Java versions are the class-file versions minus 44. A class listed by an index class that loads gives a 1000 whose text holds `java.lang.UnsupportedClassVersionError` and the same sentence; the hint of the paragraph above then gives the same specific words.

**Rejected.** *Making overrides load on v1.7.4* by generating one collecting `TLCOverrides` class: a real feature, about a week, redone when milestone 3 makes modules per project. *Refusing to run*: blocks specs whose TLA+ definitions are correct fallbacks. *Inferring a failed load from a missing 2168 line*: the line is absent for every `warn = false` override, which is what the examples use. *Passing only the classes named in service files*: drops the default class on rolling builds, see part 1.

**Tests.** Unit, `collect_override_classes` with real folders and jars from the fakes: a service file; a bare `TLCOverrides.class` in a folder and in a jar; both in one entry; a registered module's service file together with a project's own `TLCOverrides.class`, where the list holds both names. Unit, `check_overrides` with real class files: each of the four warnings and the clean case; for the fourth, a class that implements the interface only through a superclass in the same folder is not warned about, and neither is one whose superclass cannot be found. Feature, in-process: a registered module with class `QueueOverrides`, v1.7.4 pinned, `tlaup tlc Spec` prints the warning on stderr and still starts Java; with a rolling build pinned there is no warning and the logged command's property names both that class and a project `TLCOverrides`. Golden: the override cases added to the corpus ([01 T3](01-testing.md#t3-golden-files)) parse to the loaded list, the three warnings, and the exception error; research 28's two captures (2173 for a too-new index class, 1000 with `UnsupportedClassVersionError` for a too-new listed class) each give the specific hint with the right two Java versions. Integration: `docs/examples/QueueModule` on both builds ([01 T9](01-testing.md#t9-integration-tests)).

**Changelog.** Added: "tlaup warns before a run when a registered Java override class will not be loaded by the pinned TLC build. On v1.7.4 only a class named `tlc2.overrides.TLCOverrides` is loaded." Fixed: "On rolling builds an override class named `tlc2.overrides.TLCOverrides` inside a jar on the classpath stopped loading when another override module was registered." (Revised 2026-11-22, by the maintainer, from finding C1 of the [stage 4 review](../packages/review-2026-11-21.md): a Changed entry, "The run output lists the operator overrides TLC reports loading", was dropped, because nothing in the first wave prints that list; it belongs with the verbose header of milestone 4.)

**Depends on.** G1, V1 (capabilities), M2, M3 (the class-file reader). **Risks.** The capability rule is exact only for the two supported builds ([00](00-overview.md#what-a-build-can-do)). Reading the file list of every jar on the classpath costs a zip directory read per jar, once per run. The hint of part 4 is added for any early message 1000 when override classes were passed, so it can stand beside an exception that has another cause; its wording is conditional for that reason, and the one such case in the captures (v1.7.4's false `POSTCONDITION`) is excluded by the nested-message condition. Research 13 ran Java 25 only; research 28 ran the class-version cases on Java 11, 21 and 25, both builds, Linux and macOS. A check before the run that compares the newest class-file version under the project's `classes/` with the running Java (the class-file reader of M3 reads it) is possible later; it is not taken now, because the hint on 2173 already says what to do.

## R8 Passthrough and workers

Roadmap: "Pass everything after `--` to TLC. Add `--workers`, defaulting to `auto`, as the only first-class TLC option (decision D24). The existing `--cfg` and `--coverage` stay; `--coverage` remains hard-coded to `-coverage 1`."

**Problem.** Today nothing the user types reaches TLC except the spec and the cfg name; a TLC option such as `-deadlock` or `-simulate` cannot be used without leaving tlaup.

**Design.** The command declares the spec and then a variadic argument for TLC's own arguments. Typer treats everything after `--` as arguments, so `-deadlock` after `--` reaches that list, while an unknown option before `--` is still an error (unknown options are not ignored). A word after the spec that does not start with a dash also lands in the list without `--`; `--` is needed as soon as one of TLC's arguments starts with a dash, which is nearly always, and the help text shows only the `--` form. All three behaviours were tried on the locked Typer 0.29.1; research 23 found every Typer from 0.22.0 to 0.29.2 behaving as 0.29.1 in everything it checked, and the contract tests of [14 F10](14-config-and-cli.md#f10-no-tracebacks) run against the newest Typer too. The arguments become `TlcRequest.extra_args` and are placed before the spec in the command, unchanged.

`--workers TEXT`: `auto` or a positive integer; the default comes from the setting `tlc.workers`, whose default is `auto`. tlaup passes `-workers <value>`. A value that is neither is a `UsageError`, raised by the first step of the preflight with the table below (R11), before the spec is looked at and before any prompt.

Because both tlaup and the user can now give the same TLC flag, one table decides, and it is the only place such rules live (`tlaup/tlc/invocation.py`):

| Among TLC's arguments | With the tlaup option | Without it |
| --- | --- | --- |
| `-workers` | `--workers` given: `ConflictingOptions` (2) | tlaup passes no `-workers`; the user's is used |
| `-coverage` | `--coverage` given: 2 | passed through |
| `-config` | `--cfg` given: 2 | passed through; tlaup does not validate it. TLC reads a relative value against the spec's folder, not the working folder (R4) |
| `-metadir` | n/a | the user's is used; no run folder (R6) |
| `-tool` | n/a | passed through; harmless in parsed mode; in `--raw` mode it is the user's choice |
| `-generateSpecTE`, `-noGenerateSpecTE`, `-teSpecOutDir` | n/a | tlaup adds no `-noGenerateSpecTE` (R6) |
| `-recover PATH` | n/a | passed through; the recovered run's lock is held (R6) |
| `-difftrace` | n/a | passed through; the parser fills each state's unchanged variables from the state before (P5) |
| `-fp`, `-seed` | n/a | the user's are used; tlaup passes the one that is missing, chosen at random, and records both (R6, D52) |

**`auto` on both builds** (top-up, [research 19](../research/19-workers-auto.md)). Both builds accept `-workers auto`, on Java 11 and 25: it is `Runtime.availableProcessors()`, which follows `taskset` and cgroup CPU quotas, so the container case is TLC's own. tlaup passes `-workers auto` unchanged on both; the fallback the first design held in reserve (a CPU count computed in Python) is not needed. tlaup's own check of `--workers` stays strict, `auto` or a positive integer written in digits: TLC also takes `+3`, `AUTO` and ` auto `, which tlaup refuses with code 2, as an option of its own may. The start line (2187) gives the count TLC chose and not whether it came from `auto`; the resume command uses that count (R6).

**Rejected.** Scanning all extra arguments to "understand" them: only the flags in the table are looked at, by exact match, and the list is short on purpose (D24: fewer options to keep in step with TLC). Turning a conflict into "last one wins": which one TLC honours for a repeated flag was not checked.

**Tests.** Feature, in-process: `tlaup tlc Spec -- -workers 4 -deadlock` (the roadmap's exit criterion) logs a Java command ending `-workers 4 -deadlock <spec>` with one `-workers`; `--workers 2 -- -workers 4` exits 2; `--workers auto` logs `-workers auto`; `--workers 0`, `--workers x` and `--workers +3` exit 2; a mistyped `--coverge` exits 2 and starts nothing. Unit: the table, row by row. Integration: `--workers auto` under `taskset -c 0` prints a start line with `1 worker`, on both builds.

**Changelog.** Added: "Arguments after `--` are passed to TLC: `tlaup tlc Spec -- -deadlock -simulate num=10`." Added: "`--workers N|auto`." Breaking: "TLC now runs with `-workers auto` by default (was TLC's default of one worker). Set `tlc.workers: 1` or pass `--workers 1` for the old behaviour."

**Depends on.** G1. **Risks.** Several workers change the order of `Print` output and can change which counterexample is found first; this is TLC's behaviour and is named in the changelog entry.

## R9 Show command

Roadmap: "Make `--show-command` print the exact command that would run, including `-tool`, shell-quoted, without creating or deleting anything in the run cache."

**Problem.** `--show-command` builds the command with one function while the run edits the list afterwards (`-tool` is inserted later, `-coverage 1` is appended after the spec instead of before it), and building it creates a run folder and deletes others.

**Design.** `--show-command` runs the preflight, builds the `JavaInvocation` with the same function the run uses, prints `shlex.join(argv)` on stdout (one line), and exits 0. With `--raw` the printed command has no `-tool`. A GitHub token is never part of a Java command, so nothing needs hiding here; the rule that it is never printed is tested in [12 V7](12-tools-and-downloads.md#v7-github-client).

- **It never prompts and never installs** (D45). Its `get_build` is the store's pinned build; with nothing installed or nothing pinned it stops with code 3 and the hint, whatever `--auto-install` says. It does not sweep either.
- **Nothing is created in the run cache**: the run id is generated; the folder and its lock are not.
- **The lifeline is left out** (top-up, D51). The printed command has no `-javaagent` of tlaup's: a pasted command would carry the process id of a tlaup that has already exited, and its JVM would stop at once ([20 G3](20-groundwork.md#g3-java-launcher)). The encoding options (D56) and the `-fp` and `-seed` tlaup chose (D52) are in it, as they are in the run. The help of `--show-command` says in one line that the printed command does not stop TLC when the terminal that pasted it is killed.
- **What `-metadir` a pasted command uses.** The printed command names `<cache>/runs/<run-id>`, the folder a real run with that id would have used. Run by hand, that folder is not tlaup's to manage: it has no lock and no `run.json`. tlaup therefore leaves it alone unless asked: the sweep removes such a folder only after 30 days, and `tlaup cache clean` only with `--all` (R6). TLC's own timestamped folder inside it is deleted by TLC after a clean finish, as always. The help text of `--show-command` says in one line that for a long run pasted by hand the `-metadir` value should be replaced with a folder of the user's own.

On Windows `shlex.join` produces POSIX quoting; `subprocess.list2cmdline` is used there instead.

**The printed command can be pasted as it is** (top-up, [research 20](../research/20-metadir-creation.md)). The printed `-metadir` names a folder that does not exist yet; TLC creates it and every missing folder above it, on both builds, Java 11, 21 and 25, Linux, macOS and Windows. No `mkdir` line and no platform note. When the folder cannot be made (a file in the way, no permission), TLC exits 1 with a Java stack trace that names its timestamped folder before printing anything else; a pasted command shows that as printed (D9), and a real run never meets it, because `run_folder` makes the folder first and maps a failure to `FileOperationError`.

**Rejected.** Printing the command without `-metadir`: it would not be the command that runs, and a pasted run would write `states/` beside the spec. Creating and locking the folder for the printed command: the roadmap says nothing is created, and nothing would ever release the lock.

**Tests.** Feature, in-process: output is one line; it holds no `-javaagent`, and it holds the three encoding options, `-fp` and `-seed`; the cache holds no run folders and no lock files; `java` was started for nothing but the remembered version check; with no build pinned it exits 3 with one error line and no prompt, also with `--auto-install rolling`. Plain pytest, two in-process runs in one test ([01 T5](01-testing.md#t5-feature-files-and-steps)): the line equals the command logged by a real run with the same arguments apart from the run id (compared after replacing the id). Unit (`rundirs`): a folder under `runs/` with no `run.json` survives a sweep and a plain `cache clean`.

**Changelog.** Fixed: "`--show-command` printed a command without `-tool` and with `-coverage 1` in the wrong place, and created (and could delete) run data. It now prints exactly what would run and creates nothing in the run cache."

**Depends on.** G1, R6, R11. **Risks.** A user who pastes the command twice at once shares one `-metadir` between two runs, which collides on v1.7.4 in the same second (research 17); the help line about replacing `-metadir` covers it.

## R10 Project root

Roadmap (recorded without a solution): "The project-root rule counts a parent folder that has `lib/`, `modules/` or `classes/`, so a spec under `~/work` with `~/lib` present runs with `~` as its root and every jar in `~/lib` on the classpath."

**Design.** `find_project_root(spec: Path, home: Path) -> Path | None`:

1. The spec's own folder is the root if it contains `modules/`, `classes/` or `lib/`.
2. Otherwise the spec's parent folder is the root if it contains one of the three **and the spec's folder is named `spec`, `specs`, `test` or `tests`**. This is the documented layout (`project/spec/Spec.tla`) and nothing wider.
3. A folder is never the root if it is the user's home folder or a filesystem root.
4. Otherwise there is no root.

The run header in verbose mode names the root and every classpath entry it added, so a surprising root is visible.

This is a stopgap by design: milestone 3 makes the project file the marker and walks up to find it ([40](40-later-milestones.md#milestone-3-reproducibility)). The function keeps its signature then; only its body changes.

**Rejected.** Waiting for the project file: the `~/lib` case puts arbitrary jars on TLC's classpath today. Dropping the parent rule: breaks the documented `spec/` layout and the examples. Walking further up: without a marker file, more folders would qualify by accident, not fewer.

**Tests.** 0.8.x's `tests/unit/spec/test_project.py` went with the old suite in package 03b (decision D62); its five cases are taken over as inputs of the new unit test (inventory rows S8 and S9). The two where the spec's own folder holds the marker, or nothing does, are taken over as they are. The three that put the spec in a folder named `subdir` and expect the parent as root (`parent_has_classes`, `detected_by_lib`, `detected_by_modules`) contradict rule 2 and are taken over with the folder named `spec`. New cases: spec in `work/` with `lib/` in the parent (no root); spec in `tests/` with `modules/` in the parent (root); the parent is the home folder (no root); the spec's folder is the home folder and has `lib/` (no root). (Stage 4 review, 2026-11-24: the old file is not kept; its cases are inputs of the new test, finding E5.)

**Changelog.** Breaking: "A folder is treated as the project root of a spec only if it is the spec's own folder, or its parent when the spec is in a folder named `spec`, `specs`, `test` or `tests`. The home folder is never a project root. A project that keeps specs in a differently named subfolder must move `modules/`, `classes/` or `lib/` beside the specs or rename the subfolder."

**Depends on.** Nothing. **Risks.** Layouts such as `project/models/Spec.tla` with `project/lib/` stop finding the root; the changelog says what to do.

## R11 Preflight

Roadmap: "One preflight used by every `tlaup tlc` path, checking jar, Java, spec and cfg in that order, each failure a one-line error naming the next command. Print nothing, including 'Starting TLC', until the checks pass."

**Problem.** The three paths of `tlaup tlc` check different things in different orders; a missing jar or Java can print "Starting TLC" and then a traceback.

**Design.** The preflight is `resolve_tlc_invocation` ([20 G1](20-groundwork.md#g1-tlc-invocation)); there is no other way to get a `TlcInvocation`, so `--show-command`, `--raw` and the parsed run cannot skip it.

**The order is spec, cfg, tool build, Java** (decision D45), not the roadmap's jar, Java, spec, cfg. Two reasons: a mistyped spec name is reported before any first-run prompt or download; and milestone 3 chooses the build from a project file found by walking up from the spec, which needs the spec first. With this order milestone 3 adds a step and moves none.

Before those four comes a step that reads nothing from the disk: the checks that need only the command line and the environment. A mistake of that kind is a usage error whatever is installed, and reporting it first means nobody answers the first-run prompt, or waits for a download, and is then told that two of their options conflict.

| Step | Failure | Message and hint |
| --- | --- | --- |
| 0. The command line | Two options that conflict (the table of R8); `--workers` that is neither `auto` nor a positive integer; an unbalanced quote in `TLAUP_JAVA_OPTS` ([13 J1](13-modules-and-java.md#j1-java-options)) | `ConflictingOptions` or `UsageError`, code 2 |
| 1. Spec | Not found; not a spec | `SpecNotFound` with the paths tried, or `UsageError` (R5) |
| 1b. Project root | Cannot fail | `find_project_root(spec, home)` (R10). It needs only the spec, and step 2 searches the root for the cfg |
| 2. Cfg | `--cfg` given and not found | `CfgNotFound` with the paths tried (R4). With no `--cfg` nothing is checked (R4, step 6) |
| 3. Tool build | Nothing installed | The first-run prompt ([12 V9](12-tools-and-downloads.md#v9-first-run-prompt)), or `NoToolsInstalled`: "no TLA+ tools installed" / "run `tlaup tool install stable` or `tlaup tool install rolling`". With `--show-command`: always the error (R9) |
| | Builds installed, none pinned | `NoPinnedBuild`: "no version pinned" / "run `tlaup tool pin <one of: ...>`" |
| | The pin names a build that is gone or damaged | `PinnedBuildMissing`: "the pinned build rolling@bc1b506 is missing" / "run `tlaup tool install rolling` or `tlaup tool pin ...`" |
| 4. Java | Not found; too old; the check timed out | `JavaNotFound`, `JavaTooOld`, `Failed` ([13 J2, J3](13-modules-and-java.md#j2-finding-java)) |

Then the classpath and the override collection and check (warnings only, R7), which need the build, the warning for a non-ASCII spec or cfg path under a locale that is not UTF-8 (R3), and the values that depend on the build (`-noGenerateSpecTE`, R6) or are chosen per run (`-fp`, `-seed`, R6). Nothing after step 4 can fail for a reason the user caused on the command line.

So with no build installed and a missing spec, the spec is reported and the code is 4; no prompt is shown. With no build installed and `--workers 2 -- -workers 4`, the conflict is reported and the code is 2; no prompt is shown.

`sany` and `pcal` use the same steps in the same order, and `repl` steps 0, 3 and 4, through the same functions (`resolve_spec`, the command's `get_build`, `require_java`); [21](21-other-tools.md) has their one resolving function. Their step 0 holds the Java option check and, for `sany`, the refusal of `-d` ([21 S1](21-other-tools.md#s1-sany)).

Nothing is printed before the preflight returns: the reporter is created after it, the preflight's warnings come back in `TlcInvocation.warnings` and are printed by the command, and the first-run prompt is the one thing that may write (to stderr) during it.

**Rejected.** The roadmap's order: see above; the maintainer chose spec first (D45). Checking the command line where the first revision did, after Java: the conflict of two options would be reported after a prompt and a download. Checking the default `Spec.cfg` when no `--cfg` is given: R4, step 6. A separate "check" function beside the function that builds the invocation: two lists of checks that drift.

**Tests.** `tlc_errors.feature`, in-process: one scenario per row, except the Java check that timed out, each asserting the code, an empty stdout and exactly one `error:` line; for the spec, cfg and build rows that `java` was not started at all; for the Java rows that it was started for `-version` only and TLC was not started; for the build rows that the hint names a command. One scenario has no build and a missing spec and asserts code 4 and that nothing was asked; one has no build and conflicting `-workers` and asserts code 2 and that nothing was asked. The spec, cfg, pinned-build and Java rows are run for the parsed and `--show-command` paths with a scenario outline; the raw path is run as a real process for the spec row and the Java row, which is enough to show it goes through the same function. The timed-out Java check has no scenario: its timeout is ten seconds, and a scenario would wait that long on the real clock, which [01 T12](01-testing.md#t12-rules-for-writing-tests) rule 5 allows for one test only. The unit test of `ask_version` with a timeout of half a second ([13 J3](13-modules-and-java.md#j3-one-java-start)) stands in for the row: it shows the failure is `Failed` with the word "seconds", and the preflight maps that error as it maps the others. (Stage 4 review, 2026-11-24: finding C4.)

**Changelog.** Fixed: "Missing Java, a missing jar, or a missing spec could print 'Starting TLC' and then a traceback. Every `tlaup tlc` path now checks the spec, the cfg, the tools and Java first and reports the first problem in one line with the command to run next."

**Depends on.** G1, G2, R4, R5, R8, R10, V9, J2, J3. **Risks.** The spec is now looked up before tlaup knows it can run anything, so a user with nothing installed and a mistyped spec fixes the spec first and meets the install prompt on the second try.
